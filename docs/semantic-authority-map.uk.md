# Карта семантичної влади my-lisp (український супровід)

Український супровідний виклад до `semantic-authority-map.md`. Повний текст — англійською в основному файлі; це стислий переказ ключових правил.

## Одне правило

> Мова визначає власну семантику; runtime-и лише доводять відповідність їй.
> Rust знає механізми. Lisp знає мову.

Жоден implementation-файл, README-абзац, нотатка агента, бенчмарк чи історичний план не може мовчки переважити семантичний контракт.

## Порядок влади (від найвищого)

1. `language-contract.lisp` — машинно-читаний контракт і ратифіковані інваріанти.
2. **Canon `()` / Lisp-owned таблиця функцій та identity-джерела** — `lib/surface/semantic-registry.lisp`, executable Canon/law sources на кшталт `lib/canon.lisp` і ратифіковані Lisp-owned function-table metadata. Згенеровані/mechanism tables є лише проєкціями.
3. Ратифіковані ADR та виконувані докази відповідності — `tests/fixtures/conformance.lisp`, `macro-conformance.lisp` і тести, що виконують ці закони.
4. Reference implementation — `crates/my-lisp` (Rust). Це зрілий software-оракул для тестування поведінки, а не володар семантики лише тому, що написаний на Rust.
5. Незалежні реалізації — `fpga-lisp`, `c-runtime/` та інші заявлені субстрати; їхня цінність — фальсифікація implementation-specific припущень.
6. Згенерований довідник (напр. `docs/FUNCTIONS.md`) — описує поточну поверхню реалізації, але не перевизначає контракт.
7. Людська пояснювальна проза — `README.md`, `docs/language-core.md`, туторіали.
8. Історичні/процесні матеріали — `PLAN.md`, датовані аудити, нотатки агентів. Це докази історії, не чинна семантична влада.

Якщо нижчий пункт суперечить вищому — нижчий вважається застарілим до узгодження.

## Семантична ідентичність проти поверхневого написання

Написання — не є ідентичністю примітиву. **Canon `()` / Lisp-owned таблиця функцій є поточним коренем semantic dispatch.** Сім класичних операцій Маккарті (`quote · atom · eq · cons · car · cdr · cond`) лишаються historical/minimal root усередині цієї влади, але не утворюють закриту множину і не є другою таблицею семантики. `()` є ground/list identity, не “нуль результатів” для островів. Природномовні та історичні поверхні відображаються на semantic identities; зміна назви поверхні не створює новий примітив.

## Розширення файлів

Назва проєкту/репозиторію — **`my-lisp`**. Чинне канонічне розширення джерела — **`.lisp`** (згідно [my-lisp#81](https://github.com/juv4uk/my-lisp/issues/81) — розширення ніколи не є семантикою). **`.lisp`** і **`.lisp`** лишаються повністю підтримуваними legacy-псевдонімами. Окремий репозиторій `wsm` — незв'язане фундаментальне дослідження; спільні літери не перейменовують цей мовний проєкт.

## Межа host

Host-операція заслуговує на існування, якщо дає інформацію/ефект, недоступний у чистій семантиці мови, або впроваджує межу безпеки embedding, яку недовірений код не повинен вміти самому собі надати. Дві різні "політики" не можна змішувати: **семантична/прикладна політика** (що означає спостереження — переносити в Lisp, коли можливо) і **політика авторизації embedding** (які filesystem roots/процеси/адреси дозволені частково довіреній сесії — залишається на боці host, бо обмежувана програма не повинна вміти сама собі надавати дозвіл).

"Зменшуй Rust, розширюй Lisp" — це не правило безпеки, а питання семантичного володіння.


## Механізми після семантики

Executor-и, island adapters, machine lowering і generated mechanism projections не визначають значення SID. Спочатку Canon `()` / Lisp-owned таблиця функцій фіксує identity/meaning/law/domain; лише після цього механізм може бути admitted і вибраний. Generated projection має зберігати provenance до Lisp-owned authority і не може ставати input authority сама по собі.
