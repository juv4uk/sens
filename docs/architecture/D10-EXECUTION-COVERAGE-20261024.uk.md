# Д10 · 1024 ратифіковані позиції та докази виконання

Акт власника ратифікує **всі 1024/1024** десятибітні координати. Ціль архітектури — **1024 виконувані доменні функції/закони**, але саме поле реєстру не є виконанням. Не називати відсутню квитанцію «невиконуваною функцією».

Облік розділено на незалежні рівні:

1. **Кодова адреса**: 1024/1024 — незмінний pinned v18 за актом власника.
2. **Мовне визначення**: сканер concrete DEFINE/alias у `lib/core4.lisp` та `lib/epistemic.lisp`, зафіксований у `d10_definition_bindings_generated.rs`; стан цієї групи — `SOURCE_FOUND`, **не** фізичний PASS.
3. **Модельний закон**: 256 селекторів `C[AD]{8}R` мають конструктивний доказ адрес на парах; сам по собі не є нативним виконанням.
4. **Фізична семантика**: тільки позитивний і негативний Lisp/SENS-свідки через direct → Zig/T5M → paired → standalone із квитанцією exact SHA. `NOT_RECORDED` не означає `FALSE`.
5. **Ціль**: поелементна атестація всіх 1024; ні один із 1024 не переведено у статус «за визначенням невиконуваний».

Для кожної координати згенерувати механічний облік:

```sh
python3 scripts/check_d10_owner_whole_domain_ratification.py --self-test --coverage-tsv /tmp/d10-execution-coverage.tsv
```

TSV містить рівно 1024 рядки та `stable_id`; статус `NOT_ATTESTED_HERE_NOT_A_NONCALLABLE_VERDICT` означає, що **цей checker** не запускає SENS. Вхідний v18 залишається незмінним і Git-pinned. Нові квитанції перевіряти на тому самому SHA окремим нативним маршрутом, а не змінювати історичну ратифікацію.

Перший точковий нативний свідок: `tests/semantic/d10-empty-queue-law.lisp`; мутант — `tests/semantic/d10-empty-queue-mutant.lisp`. Обидва виконують ратифіковану D10:0011000010 `черга-порожня?` у SENS. `NATIVE_SENS_POSITIVE` та `NATIVE_SENS_NEGATIVE` отримують PASS тільки з hosted-логу точного SHA.

**Наступний таргет**: установити дійсні джерельні визначення для решти адрес, нарощувати F1/F2/F3/F4 по `stable_id`, доводити нативним SENS; не призначати нові коди чи глобально знімати fail-closed захист.
