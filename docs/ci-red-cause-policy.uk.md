# Червоний CI: маршрутизація причин (операційне правило)

Це **операційний шар**, не другий контракт семантики SENS. Мову визначають точні біти, домен та ратифікований закон; Python тільки транспортує й перевіряє метадані.

## Два незалежні виміри

| Причина | Відповідальний | Умова закриття |
|---|---|---|
| OWNER_UNCLEAR | власник `juv4uk` лише один раз | точне письмове ратифіковане правило (`ratified_rule`), а також доказ CI |
| AGENT_DEFECT | рій | атомарне виправлення та CI-доказ |
| TEST_DEFECT | рій | виправлення тесту без заміни SENS-семантики, CI-доказ |
| LEGACY_BINDING | рій; власник тільки для нормативного вердикту | `legacy_marker` (SID8/десятковий посередник/спадковий синтаксис), `provenance`, міграція або доведений історичний статус |

Окремий статус **REGRESSION / TRANSITIONAL / FLAKE** регулюється чинним `scripts/ci_failure_contract.py` та `knowledge/red-test-quarantine.json`. Цей механізм його не замінює. Не підмінювати недоведені регресії штампом REGRESSION. Відсутність причини/статусу: UNCLASSIFIED і блокувальна відмова негайно; після 24 годин — ESCALATE_24H. Іменований чинний карантин не означає некласифікованість.

## Запис у журналі

Кожний `cases[]` з `knowledge/red-cause-ledger.json`: `run_id`, точний `run_url`, `first_seen_at` (з поясом часу), `cause`, `stamp`, `owner`, `state: open|resolved`. Для FLAKE і TRANSITIONAL: `ticket: #N`, `since`, `expires`, `investigation`. Для LEGACY_BINDING: `legacy_marker`, `provenance`. Для доведеного розв'язання: `proof_run_url`, `proof_sha` (40 hex), `resolved_by: swarm|owner`. Для OWNER_UNCLEAR: `ratified_rule` (посилання на чинну доктрину, не новий паралельний авторитет). 

Жодний агент не створює ратифікацію самостійно; лише додає перевірений запис до чинної доктрини після рішення власника. Відсутній доказ CI не можна рахувати як виправлення.

## Запуск

- `python3 -m unittest discover -s tests -p 'test_red_cause_router.py' -v` — 8 негативних/позитивних механічних перевірок.
- `python3 scripts/red_cause_router.py audit` — аудит журналу й частки підтверджених виправлень без власника.
- `GITHUB_TOKEN=... python3 scripts/red_cause_router.py live` — перелік падінь GitHub Actions за останні 48 годин (за замовчуванням), включно з workflow-level failures із `jobs=[]`.

Обмеження пілота: live-інвентар перевіряє **workflow conclusion=failure** і обмежене вікно, не всі види `cancelled`/`timed_out`; після межі сторінок виводить INCOMPLETE_INVENTORY і завершується червоним. Він не збирає приватні job logs, не створює GitHub issues і не привласнює причину на підставі назви тесту. Автоматичне створення задач/assignments та історичне покриття всіх 600 workflow — окремий етап із доказом, не заявлена готовність.

Метрика: verified_swarm / verified_total. Offline-аудит перевіряє лише повноту метаданих, live-аудит додатково звіряє GitHub API: завершений успішний CI-run, точний commit SHA та URL. Непідтверджений доказ дає `UNVERIFIED_PROOF_RUN` і блокувальне RED. Це не доказ семантичної справності SENS.

Першоджерела: GitHub Actions workflow commands (офіційна документація); CI-договір #5741; координація #5029. TECH-SCAN проведений 2026-10-13.

## Автоматичний карантин RED віком від 24 годин (13.10.2026)

Операційний, **не тестовий** карантин: сканер `scripts/aged_red_quarantine.py` раз на дві години знаходить `workflow_run.conclusion=failure` віком ≥24h; заносить у стабільний, оновлюваний коментар issue #5741 стан `Q_TRIAGE_24H`, workflow, гілку, URL, точний SHA, час і власника первинного розбору (`swarm`). Оригінальний GitHub status залишається **failure**, жодний required gate не вимикається. Вік сам не визначає `FLAKE`, `TRANSITIONAL` чи причину з чотирьох класів. Цю класифікацію рій робить після аналізу фактичних логів; нормативні уточнення лишаються за власником.

Початкове рухоме вікно — 7 діб, тобто для наявних запусків старше 7 днів жодного твердження про карантин не робимо. GitHub має обмеження 1000 runs на один пошуковий зріз: сканер ділить діапазон на добові запити, а при 1000+ результатів рекурсивно звужує часовий інтервал; лише нероздільний або неповний інтервал позначає `INCOMPLETE_API` з nonzero. Таблиця групує запуски за workflow+branch, але лічильник включає всі підтверджені у вибірці run IDs. Оновлюється один і той самий коментар, щоб не плодити сотні задач. Перевірка: `python3 -m unittest discover -s tests -p 'test_aged_red_quarantine.py' -v` (один точковий тест межі та відсутності false green). Live publishing потребує GitHub `actions:read` та `issues:write`.

## Миттєвий карантин RED workflow (13.10.2026)

Окремо від 24-годинного історичного обліку діє `Q_WORKFLOW_NOW` для поточного `main`: `scripts/quarantine_red_workflows.py` із GitHub REST виявляє завершені `conclusion=failure` на точному head SHA і оновлює **один** коментар у #5741. Запускається при `push` цього CI-файлу, після завершення дев'яти поточних проблемних workflow через `workflow_run.completed`, а також резервно раз на 15 хвилин (фактичний розклад GitHub може запізнюватися). Жодний workflow не вимикаємо й не переводимо в FLAKE на підставі кольору. Не запускалися на head — не вважаються green; ще незавершені — фіксуємо кількість. Рій отримує механічний `UNCLASSIFIED` і збирає докази першопричини.

Вхідні дані від `workflow_run` не виконуються; сканер читає поточну `main` через GitHub API із `actions:read`, записує один коментар з `issues:write`. Жодних артефактів або коду з неперевірених гілок не завантажує. Workflow обсерватора виключений із власної черги, але його GitHub RED, якщо виникне, не приховується. Перевірка: `python3 -m unittest discover -s tests -p 'test_quarantine_red_workflows.py' -v`.
