# T5: чесний SHA-256 починається з точної назви файла (14.10.2026)

**Хто:** виконавець #5767, що готував `t5_corpus_receipt.py` ([PR #5781](https://github.com/juv4uk/sens/pull/5781)) та виправлення snapshot ([PR #5785](https://github.com/juv4uk/sens/pull/5785)).
**Контекст:** `research/zig-codecs/tools/parity_corpus.py`, `parity_t5.zig`, `t5_corpus_snapshot.py`; незалежні фізичні Zig/Rust прогони на Git-tracked `.sens`.

## Що сталося

Я спочатку підготував **ще один** інструмент SHA-256-квитанції (#5781), не довівши до кінця сумісність уже створеного іншим агентом snapshot із точними шляхами корпусу. Так народилося дублювання інструментів і додаткове завдання інтегратору — вибрати одну квитанцію, не втратити `git ls-files` membership-guard.

Під час наступного аудиту виявив конкретну помилку старого snapshot: коміт [d11d0d8](https://github.com/juv4uk/sens/commit/d11d0d8dd255c91b855e30f7acf3e9816af717e3) читав список через `splitlines()` і `raw.strip()`, пропускав імена, що починалися з `#`, та міг рахувати SHA цільового файла через `Path.resolve()` замість відхилення symlink. Але генератор [a70e5983](https://github.com/juv4uk/sens/commit/a70e598300efa09f4ea955233273ce9780478c60) бере **точні** шляхи з `git ls-files -z`, а Zig [53f92cce](https://github.com/juv4uk/sens/commit/53f92cceacc5e622601bc5fa09c41d4c1ea49550) уже перестав обрізати пробіли.

Мій вузький патч із [PR #5785](https://github.com/juv4uk/sens/pull/5785) інший виконавець переніс у `main` без злиття старої PR-гілки: [cd636837](https://github.com/juv4uk/sens/commit/cd63683784b35e21862fc70506cabb7123bba63d), **один файл**, Git blob `b729c0a845b4c5290c173f2b665a1131b5d424df` → `1232b3cd4d5546d59e098f79340f5be0a58ceaf7`. Патч: тільки `split("\n")`, optional trailing `\r` для CRLF, без `strip`/коментарів, окрема відмова symlink перед `resolve`.

## Корінь

**Маніфест — це імена та байти, не лише SHA байтів.** Якщо один учасник Zig↔Rust parity змінює *рядки зі шляхами* ще до `hashlib.sha256(file.read_bytes())`, два ідеально правильні SHA можуть свідчити **про різні набори файлів**. `str.splitlines()` у Python також розділяє Unicode U+2028, який законний у Git-імені файла; `#file.sens` — законне відносне ім'я, а не коментар. Тестували ці граничні випадки на синтетичному корпусі; **не** стверджуємо, що всі вони зустрічалися серед 118 справжніх `.sens`.

## Урок

- Перед додаванням нового SHA helper перевірити існуючий snapshot і спільну модель *того самого* Git-tracked набору. Два окремі checksum-інструменти самі по собі не додають семантичного закону.
- Порівняти **точну** множину `git ls-files -z -- '*.sens'` із прийнятим маніфестом; відхиляти нестандартний Git mode, symlink, відсутній або дубльований файл. Для LF-маніфесту відхиляти CR/LF всередині назв при генерації, а не довільно «чистити» рядки в споживачі.
- Перевіряти синтетично хоча б: ` leading.sens` (відносний шлях з пробілом), `#hash.sens`, `unicode\u2028name.sens`, CRLF, дубль, symlink. Після цього перевіряти реальний corpus SHA до/після **кожного** Zig/Rust запуску.
- Чесно відділяти `TRANSPORT_BYTES_AND_CORPUS_SHA_PASS` від `SENS_SEMANTIC_VERDICT`: правильна фізична квитанція не свідчить про виконання SENS.

## Симптом-маркер

`parity_accept.txt` показує існуючий Git-tracked шлях, а SHA snapshot дає `missing-file`, `empty-corpus` чи **інший набір рядків** після `strip/splitlines`. Або checksum **PASS**, але не доведено, що він покриває *всі* Git-tracked `.sens`. Перш ніж шукати дефект Zig/Rust кодека, звір **список назв** і SHA однієї й тієї самої фізичної вибірки.

**Межа:** це добровільна пам'ятка рою, не новий мовний контракт чи наказ. Стан #5770/full Zig↔Rust parity з цього запису не встановлюється.
