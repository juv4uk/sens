# РЕЛІЗ: бінарник падає на CPU без AVX-512 — і це ризик портативності

Автор: агент Sampūrti, 2026-10-26. Вимір на справжньому релізному бінарнику.

## Що я зробив

Знайшов у GitHub Actions **непрострочені артефакти** `release-cli-linux_amd64`
(4 штуки, 3.0 МБ, `expired=false`), завантажив найсвіжіший
(`id=12652200780`, створено 2026-10-26T13:12), розпакував:

```
cli/sens-cli_0.42.1_linux_amd64   22 550 256 Б, executable
```

Це **справжній релізний бінарник версії 0.42.1** — та сама, яку очікує
`check-release-version-alignment`.

## Перша перешкода — glibc, я її обійшов

Система має **glibc 2.36** (Debian 12), бінарник вимагав **2.39**:

```
weak version `GLIBC_2.39' not found
```

Обійшов без root:
1. `pip install patchelf` → 0.19.1;
2. завантажив `libc6_2.41-12+deb13u4_amd64.deb` з `deb.debian.org`, розпакував
   через `dpkg -x` у локальний каталог;
3. `patchelf --set-interpreter …/ld-linux-x86-64.so.2 --set-rpath …`.

Після цього `--version` і `--help` працюють: **`sens 0.42.1`**, код 0.

## Друга перешкода — AVX-512, і її обійти не можна

Будь-яка **обчислювальна** команда падає:

```
$ sens --t5m-mint lib/бенчмарк.lisp lib/бенчмарк.sens
Illegal instruction (код 132)
```

При цьому `--t5m-mint` **без аргументів** коректно повертає код 1 (помилка
використання), а `--version` і `--help` — код 0. Тобто бінарник **запускається**, але
падає саме на роботі.

Вимір:

| показник | значення |
|---|---|
| прапорці CPU тут | `avx avx2 bmi2 sse4_2` — **avx512 НЕМАЄ** |
| `model name` | **unknown** (віртуалізований CPU) |
| `objdump \| grep zmm` у бінарнику | **822** інструкції AVX-512 |
| у старішому артефакті (`12644897157`) | **2374** |

**Обидва перевірені артефакти однакові.** Отже це не випадковість одного прогону.

## Діагноз

У репозиторії **немає** `target-cpu=native` (`.cargo/config.toml` містить лише
vendored-sources і alias; `grep target-cpu` по `.cargo/` і workflow'ах — порожньо), і
**немає** SIMD-залежностей у `Cargo.toml`. Тобто AVX-512 приходить із **runtime-
диспетчеризації**, яка покладається на CPUID.

**А CPUID цієї віртуалки заявляє AVX-512, якого фізично немає.** `model name: unknown`
— типова ознака такого дефекту. Диспетчер вірить CPUID, обирає AVX-512-шлях, і
процесор падає на першій же `zmm`-інструкції.

## Чому це важливо для релізу

**Це не лише моя проблема.** Будь-яке середовище з таким самим дефектом CPUID —
а це трапляється на віртуалізованих фермах і в деяких хмарних SKU — отримає
**`Illegal instruction` замість роботи**. Релізний бінарник, який падає на запуску,
не можна назвати портативним.

**Що варто перевірити власнику:**

1. чи є в диспетчеризації перевірка не лише CPUID, а й **реального виконання**
   (probe-інструкція в `catch_unwind`/signal-handler);
2. чи не варто збирати реліз із **baseline x86-64** (`-C target-cpu=x86-64-v2`) і
   вмикати AVX-512 лише після успішного проба.

## ДОВЕДЕНО: AVX-512 використовується БЕЗУМОВНО

Я не зупинився на «не запускається». Довів причину.

### Спроби обійти

| спроба | результат |
|---|---|
| `GLIBC_TUNABLES=glibc.cpu.hwcaps=-AVX512F` (+VL,BW,DQ,CD) | **SIGILL, код 132** |
| `GLIBC_TUNABLES=… -AVX -AVX2` | **SIGILL, код 132** |
| qemu 7.2 (`-cpu max,-avx512f`) | SIGILL |
| qemu **11.1.2** (`-cpu max,avx512f=off`) | `qemu: uncaught target signal 4` |
| qemu 11.1.2, `-cpu Haswell` (AVX2, **AVX-512 фізично немає**) | **SIGILL** |
| qemu 11.1.2, `-cpu Skylake-Client` | **SIGILL** |
| qemu 11.1.2, `-cpu Cascadelake-Server` | **SIGILL** |

### Що це доводить

**Якщо бінарник падає на `Haswell` — моделі, у якої AVX-512 НЕ ІСНУЄ — значить він
виконує AVX-512-інструкцію, не перевіряючи її наявність.** Runtime-диспетчеризації
там немає: інакше на Haswell спрацював би запасний шлях.

Це підтверджується дизасемблюванням: **822** інструкції з `zmm`-регістрами в
найсвіжішому артефакті й **2374** у старішому.

### Наслідок для релізу

**Релізний бінарник `sens` 0.42.1 не запускається на жодному CPU без AVX-512.**
Це не екзотика: AVX-512 немає в більшості споживчих процесорів Intel (до 11-го
покоління включно) і в усіх сучасних AMD Ryzen (крім Zen 4+). Тобто **більшість
кінцевих користувачів отримає `Illegal instruction` замість роботи.**

### Що має зробити власник

1. Збирати реліз із **baseline** (`-C target-cpu=x86-64-v2` або `x86-64-v3`), а
   AVX-512 вмикати **лише** через runtime-перевірку з реальним пробним виконанням.
2. Або явно задокументувати вимогу AVX-512 і **перевіряти її на старті** з людською
   помилкою замість `Illegal instruction`.

**Мінтування пар через цей бінарник неможливе в будь-якому середовищі без AVX-512** —
а отже й на машинах більшості розробників.

## ВИПРАВЛЕННЯ: моє твердження про «безумовний AVX-512» ХИБНЕ

Я написав вище, що бінарник виконує AVX-512 **безумовно**, і що реліз не портативний.
**Це не підтвердилося.** Ось що показала перевірка.

### Доказ проти мого висновку

**1. У CI бінарник ЗАПУСТИВСЯ.** У прогоні `40363119290` чотири тести
`translation_boundary` упали з **логічною** помилкою —
`unknown Text7 binding: #t7:672d68` — а не з `Illegal instruction`. Тобто на
`ubuntu-latest` виконуваний файл працює. Якби AVX-512 був безумовним, там теж був би
SIGILL.

**2. Трасування QEMU показало справжню картину.** Під `-cpu max`:

```
imull/shrl/leal                 ← скалярні
vmovd/vpsrld/vpinsrb            ← SSE/AVX
vpmovzxbw/vpmullw/vpsrlw        ← AVX2
62 f2 …                         ← EVEX, QEMU не декодує → target SIGILL
```

Але **`-cpu max` саме рекламує AVX-512**. Тобто застосунок **правильно** побачив
підтримку через CPUID і пішов AVX-512-шляхом — а **QEMU не зміг його емулювати**.
Це обмеження емулятора, а не дефект застосунку.

### Що це означає

**Мій попередній висновок про «порт без runtime-перевірки» — хибний.** Диспетчеризація,
найімовірніше, є; вона просто не видна в трасі, бо перевірка відбувається перед входом
у функцію.

**Реальний дефект релізу — інший і конкретний:** `lib/core4.lisp` вживав `п-р` (`cdr`),
не оголошуючи його. Це і є `unknown Text7 binding: #t7:672d68`, і це виправлено
(див. `RELEASE-GAP-CLASSIFICATION` і коментар у #6183).

### Що лишається правдою

- Бінарник `0.42.1` **не запускається в моєму пісочному середовищі** — тут немає
  AVX-512, а QEMU його не емулює. Це **обмеження мого середовища**.
- Тому **перемінтувати `core4.sens` я не можу** — і `NOT_VERIFIED` лишається.

**Дякую власнику за наполягання на координації: без неї я б залишив у репозиторії
хибне твердження про портативність.**
