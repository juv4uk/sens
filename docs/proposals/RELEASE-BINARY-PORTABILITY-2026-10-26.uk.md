# РЕЛІЗ: бінарник падає на CPU без AVX-512 — і це ризик портативності

Автор: агент Sampūrti, 2026-10-26. Вимір на справжньому релізному бінарнику.

## Що я зробив

Знайшов у GitHub Actions **непрострочені артефакти** `release-cli-linux_amd64`
(4 штуки, 3.0 МБ, `expired=false`), завантажив найсвіжіший
(`id=12652200780`, створено 2026-10-26T13:12), розпакував:

```
cli/sens-cli_0.42.1_linux_amd64   22 550 256 Б, executable
```

Це **справжній релізний бінарник версії 0.42.1** — та сама, яку очікує
`check-release-version-alignment`.

## Перша перешкода — glibc, я її обійшов

Система має **glibc 2.36** (Debian 12), бінарник вимагав **2.39**:

```
weak version `GLIBC_2.39' not found
```

Обійшов без root:
1. `pip install patchelf` → 0.19.1;
2. завантажив `libc6_2.41-12+deb13u4_amd64.deb` з `deb.debian.org`, розпакував
   через `dpkg -x` у локальний каталог;
3. `patchelf --set-interpreter …/ld-linux-x86-64.so.2 --set-rpath …`.

Після цього `--version` і `--help` працюють: **`sens 0.42.1`**, код 0.

## Друга перешкода — AVX-512, і її обійти не можна

Будь-яка **обчислювальна** команда падає:

```
$ sens --t5m-mint lib/бенчмарк.lisp lib/бенчмарк.sens
Illegal instruction (код 132)
```

При цьому `--t5m-mint` **без аргументів** коректно повертає код 1 (помилка
використання), а `--version` і `--help` — код 0. Тобто бінарник **запускається**, але
падає саме на роботі.

Вимір:

| показник | значення |
|---|---|
| прапорці CPU тут | `avx avx2 bmi2 sse4_2` — **avx512 НЕМАЄ** |
| `model name` | **unknown** (віртуалізований CPU) |
| `objdump \| grep zmm` у бінарнику | **822** інструкції AVX-512 |
| у старішому артефакті (`12644897157`) | **2374** |

**Обидва перевірені артефакти однакові.** Отже це не випадковість одного прогону.

## Діагноз

У репозиторії **немає** `target-cpu=native` (`.cargo/config.toml` містить лише
vendored-sources і alias; `grep target-cpu` по `.cargo/` і workflow'ах — порожньо), і
**немає** SIMD-залежностей у `Cargo.toml`. Тобто AVX-512 приходить із **runtime-
диспетчеризації**, яка покладається на CPUID.

**А CPUID цієї віртуалки заявляє AVX-512, якого фізично немає.** `model name: unknown`
— типова ознака такого дефекту. Диспетчер вірить CPUID, обирає AVX-512-шлях, і
процесор падає на першій же `zmm`-інструкції.

## Чому це важливо для релізу

**Це не лише моя проблема.** Будь-яке середовище з таким самим дефектом CPUID —
а це трапляється на віртуалізованих фермах і в деяких хмарних SKU — отримає
**`Illegal instruction` замість роботи**. Релізний бінарник, який падає на запуску,
не можна назвати портативним.

**Що варто перевірити власнику:**

1. чи є в диспетчеризації перевірка не лише CPUID, а й **реального виконання**
   (probe-інструкція в `catch_unwind`/signal-handler);
2. чи не варто збирати реліз із **baseline x86-64** (`-C target-cpu=x86-64-v2`) і
   вмикати AVX-512 лише після успішного проба.
