# ADR: результати міркування першого класу як дані Lisp

Статус: **РЕАЛІЗОВАНО ЯК ЯВНО ПІДКЛЮЧУВАНУ БІБЛІОТЕЧНУ УГОДУ; МЕЖУ ЧЕСНОСТІ ОНОВЛЕНО 2026-09-17.**
Початково запропоновано 2026-08-18 як `MYLISP-UNKNOWN-RESULT-SEMANTICS-DESIGN`.
Це й надалі рішення рівня бібліотеки/API, а не зміна мовного контракту: нового
механізму винятків evaluator-а і нового Rust-варіанта `Value` немає.

Початковий дизайн називав `unknown / partial / blocked / disputed`. Реалізація
Advice Taker B1 доповнила цю алгебру станами успіху та некоректного вводу,
потрібними їй самій: `proved` і `invalid`. Існуючі `reason` та `reason-in`
залишаються сумісними; до шару спостережень викликач переходить явно через
`reason-observe` / `reason-in-observe`.

Пізніший контракт чесності міркування #219/#244 звужує умови, за яких можна
повертати багатші теги. Тег є позитивним епістемічним твердженням, а не новим
написанням будь-якого порожнього результату пошуку. Зокрема, сама відсутність
доказу не встановлює `unknown`.

## Проблема

Історично `lib/reason.lisp` повертає список результатів доказу при успіху та
`()` при невдачі. Цей сумісний API корисний, але саме по собі `()` не говорить,
чому звичайного результату доказу немає. Багатші спостереження корисні лише
тоді, коли reasoner має підставу для названої відмінності:

1. **Unknown** — окремий названий контракт повноти/пошуку позитивно встановив,
   що суб'єкт не доведено у визначеній ним області. Самої відсутності
   позитивного й протилежного доказу недостатньо.
2. **Partial** — обмежений пошук дав лише обмежений результат; це не доказ того,
   що відповіді поза межею немає.
3. **Blocked** — обчислення навмисно не продовжилося, бо не виконано операційну
   передумову. Відомо відсутній модуль належить саме сюди.
4. **Disputed** — взаємовиключні сторони обидві мають живі докази міркування.
5. **Invalid** — форма запиту/вводу некоректна; це спостереження валідації
   вводу, а не логічне `unknown`.
6. **Proved** — існує один або кілька результатів доказу, і їх треба зберігати,
   а не стискати до булевого значення.

Правило чесності навмисно асиметричне: багатша класифікація потребує позитивного
обґрунтування. Якщо жодну сторону не доведено і жоден названий контракт не
встановлює більшого, неспеціалізований результат лишається Каноном 0 `()`, а не
вигаданим `unknown` чи хибністю.

## Рішення: одна алгебра тегованих результатів, без паралельного словника

У `lib/result-status.lisp` доступні такі data-only форми:

```lisp
(proved statement results)
(unknown subject)
(partial value bound)
(blocked reason)
(disputed evidence)
(invalid reason payload)
```

Це звичайні списки Lisp. Жодного host exception type чи evaluator primitive не
додається.

Сам факт існування конструктора не дає кожному викликачеві права породжувати
цей статус. `contracts/reasoning-honesty-contract.lisp` володіє поточною межею
спеціалізації: `unknown` потребує названого контракту повноти/пошуку; повністю
перевірена відсутність модуля є `blocked`; звичайне спостереження
«жодну сторону не доведено» лишається `()`.

`proved` зберігає **всі** успішні результати `reason`, а не лише перший. Це
важливо, бо backward reasoning цілком законно може мати кілька підстановок або
шляхів доказу.

`disputed` так само зберігає докази для обох сторін. Це не інше написання
`unknown`: воно позитивно стверджує, що несумісні сторони обидві підтримані.

## Межа сумісності

Історичні API навмисно не змінюються:

```text
reason / reason-in
    -> історичний proof-list-or-() результат

reason-observe / reason-in-observe
    -> структуроване спостереження, коли воно обґрунтоване, інакше неспеціалізоване ()
```

Це дозволяє наявним споживачам мігрувати свідомо, без одночасної семантичної
зміни всіх reasoning-користувачів.

Адаптери зараз спостерігають явні позитивні/протилежні докази так:

```text
лише позитивний   -> (proved positive-goal all-positive-results)
лише протилежний  -> (proved opposite-goal all-opposite-results)
обидва             -> (disputed ((proved ...) (proved ...)))
жодного            -> (), якщо окремий названий контракт не встановлює більшого
некоректна мета    -> (invalid invalid-goal payload)
відсутній модуль   -> (blocked (module-not-found name))
```

Перевірка протилежної сторони використовує явне знання, а не
negation-as-failure: відсутність позитивного доказу ніколи не створює
негативного факту. Те саме правило доказовості тепер діє і для `unknown`:
відсутність обох доказів не створює класифікацію `unknown` без окремого
контракту, який її обґрунтовує.

## Межа представлення

`lib/narrate.lisp` може представляти теговані спостереження людині, але
presentation не є семантичною владою. `narrate-outcome` зберігає вже встановлений
клас результату видимим, щоб `unknown`, `partial`, `blocked`, `disputed` та
`invalid` не злилися мовчки в одну фразу.

Викликач і надалі може законно передати presenter-у явно встановлене значення
`(unknown subject)`. Цей закон представлення незалежний від суворішого правила
reasoner-а щодо того, коли він узагалі має право створювати `unknown`.

## Виконувані докази

Поточна семантична влада належить Lisp:

- `contracts/reasoning-honesty-contract.lisp` формулює
  `no-proof-is-not-negation`, `no-evidence-is-not-unknown` і
  `missing-module-is-blocked`;
- `tests/fixtures/reason-observe-honesty-v1.lisp` виконує випадок без доказів і
  вимагає Канон 0 `()`;
- `lib/result-status.lisp` реалізує ту саму межу спеціалізації для
  `reason-observe` і `reason-in-observe`;
- witness представлення явно встановленого `unknown` має жити в Lisp-доказах,
  а не в Rust-тесті, який спочатку вигадує `unknown` із відсутності доказу.

Rust-тести можуть спостерігати механізм та інтеграцію, але не володіють
очікуваною епістемічною класифікацією. Історичні host-side тести, що кодують
старе правило `neither -> unknown`, є застарілими дублями й мають видалятися
лише після того, як будь-який унікальний закон представлення з них збережено у
Lisp.

## Не-цілі

- Жодної зміни evaluator-а.
- Жодного нового Rust-варіанта `Value`.
- Жодної автоматичної заміни результатів `reason`/`reason-in`.
- Жодного твердження, що звичайний необмежений reasoner зараз породжує bounded
  `partial`; цей тег існує для обмежених викликачів, які справді мають таке
  спостереження.
- Жодного мовчазного перетворення операційних відмов на `unknown`.
- Жодного висновку, що Канон 0 означає false, refuted або unknown.
- Жодного глобального визначення `unknown` без названого контракту, який задає
  область, у межах якої недоведеність була встановлена.

Цей ADR фіксує поточну реалізовану бібліотечну угоду разом із пізнішим
обмеженням reasoning-honesty. Будь-який майбутній search-scoped контракт
`unknown` має явно називати свою область/доказ повноти й додавати виконувані
Lisp-witnesses; він не може відновити `unknown` як стандартне значення
відсутності доказу.
