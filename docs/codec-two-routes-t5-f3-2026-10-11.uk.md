# SENS: два production-маршрути — T5 і Frame3 Carrier (F3C) для дуже малих програм

**Рішення власника 11.10.2026:** стискання не розширюємо нескінченно. Потрібні **два** практичні production-маршрути, не три/чотири конкуруючі формати: **T5** та **Frame3 Carrier (F3C)**. Історичні CLI-команди, артефакти й частина коду ще скорочують F3C до `F3`; це сумісна стара назва, не третій формат. Їхня семантика — ті самі точні слова й D1–D9; жодних змін доменів.

**Frame3-Micro (F3M)** належить до того самого компактного сімейства, але
є окремим bounded micro-profile з зовнішнім вибором профілю. Він не додає
третій production-маршрут. Для доведеного класу F3M уже зберігає справжню
виконувану SENS-програму в **1 фізичному байті**, після чого відновлені
точні слова виконує той самий SENS evaluator. E1/E2/E3 — окремі
metadata-heavy Envelope, історично S3/v1-v3, і не називаються версіями F3.
Див. [чинну номенклатуру](codec-naming-2026-10-12.uk.md).

## Маршрути

Нормативна матриця режимів: [режими проєкту](project-modes-2026-10-12.uk.md).


| Умова | Кодек | Зовнішній формат | Призначення |
|---|---|---|---|
| Будь-яка канонічна програма, типово; невдала F3 | **T5** | `.sens` | Повні й великі програми, сумісність та перевірений виробничий reader |
| T5-представлення **не більше 16 фізичних байтів**, F3C підтримує форму, точний roundtrip, а **повний F3C носій менший** | **Frame3 Carrier (F3C; історично F3)** | `.senc`, перший байт `F3` (hex `0xf3`) | Дуже короткі програми, економія лише якщо вона справжня |

**16B — первинна обережна політика вибору**, не математична межа Рамки-3. Жодне «невдале стискання» не є помилкою програми: при відмові кандидата F3 лишається T5. Проте **під час декодування** `.senc` помилка — це помилка, не привід виконати байти як T5.

T5 зберігає всі слова, включно з W1..W9, `00/01/10/11` як точними D2, провідними нулями і роздільниками. F3 не має права «канонізувати» QUOTE-дані або перетворювати невиконувані структури на інші слова.

**Оновлено:** чинний sens-trit має явні команди encode-f3 для маленького T5 .sens, open-f3, decode-f3, eval-f3 для .senc; звичайні .sens маршрути зберігають T5. Явний декодер обмежений програмами до 16 фізичних байтів T5, вимагає мітку 0xf3, відновлює точні слова і викликає той самий виробничий SENS читач/виконавець. **Автовизначення F3, неявного виконання або декодерного fallback немає.**

## Атомарний робочий свідок (у main)

[crates/sens/examples/two_codec_small_programs.rs](../crates/sens/examples/two_codec_small_programs.rs) — Rust example, який **не змінює** production loader:

```sh
cargo run --locked --release -p sens --example two_codec_small_programs -- --self-test
cargo run --locked --release -p sens --example two_codec_small_programs -- --report
cargo run --locked --release -p sens --example two_codec_small_programs -- --convert path/to/input.sens /tmp/output-stem
```

Третя команда створює `/tmp/output-stem.senc` або `/tmp/output-stem.sens` через `create_new`, не перезаписує наявного файла, не змінює вхідний T5. Проводить декодування обраного носія **через заявлений формат**, перевіряє канонічний T5 reader та **точну рівність кожного вихідного фізичного байта**. Вибір на користь F3 — лише якщо `len([0xf3] + F3-body) < len(T5)`. При рівності вибираємо T5.

Звіт `--report` читає **всі git-tracked `*.sens`** без ручного cherry-pick, показує рішення, розмір обох носіїв за можливості, статус і фактичний файл. Позитивний тест вимагає, щоб серед них було хоча б по одному T5 та F3, і сумарний результат був менший за повний початковий T5-корпус. [CI тут](../.github/workflows/two-codec-small-f3-policy.yml).


## Явний робочий маршрут CLI (перевірено на реальних фізичних файлах)

~~~sh
cargo build --locked --release -p sens-cli --bin sens-trit

# .senc необхідно заздалегідь створити лише за допуском tiny F3:
target/release/sens-trit encode-f3 /tmp/short.sens  # створить short.senc без перезапису
target/release/sens-trit open-f3 /tmp/short.senc
target/release/sens-trit decode-f3 /tmp/short.senc
target/release/sens-trit eval-f3 /tmp/short.senc

# T5 без змін:
target/release/sens-trit open tests/fixtures/migration-quote-cohort-main/quote-legacy.sens
~~~

Явний маршрут реалізований у [bounded F3 decoder](../crates/sens/src/frame3_small.rs)
і [CLI sens-trit](../crates/sens-cli/src/bin/sens-trit.rs), використовує той самий
production canonical T5/D2 parser і pure SENS evaluator; F3 не має окремих
семантичних правил. Для .sens звичайні open/view/decode/eval збережено;
однопараметричне .senc не відкривається і не виконується мовчки.

[Успішний CI #38170264184](https://github.com/juv4uk/sens/actions/runs/38170264184)
на SHA e1dc3384b53e61e17e25fcf4f74fdb04bcfa890a перевірив усі **9 F3**
кандидатів із повного корпусу **23** tracked файлів: для кожного збіглися
open, decode і eval через T5 та явний F3; перевірено wrong-marker,
invalid extension, порожнє й завелике F3. [Артефакт реальних файлів і
результатів CLI](https://github.com/juv4uk/sens/actions/runs/38170264184/artifacts/11713558135).

**Остаточний позитивний тест encoder+decoder:** [CI #38170817413](https://github.com/juv4uk/sens/actions/runs/38170817413) на SHA 2ac5cbe001dcc949561aeb6bca231e52befd75a7. Створено справжній 3B F3 з 4B T5 через штатну encode-f3; байти однакові з відомим зразком, оригінальний T5 незмінений, подвійний запис відхилено, завеликі програми відхилено; open/decode/eval parity для всіх 9 F3 кандидатів — PASS. [Бінарний артефакт](https://github.com/juv4uk/sens/actions/runs/38170817413/artifacts/11714003230).

**Межа безпеки:** початковий F3 0xf3 + rank не має CRC/MAC.
Якщо пошкодження випадково перетворює файл на **інший допустимий фізичний
F3**, сам декодер не може визначити підміну; для публікації за межами
перевіреного каталогу потрібна довірена контрольна сума маніфесту або
криптографічний підпис. Stage manifest уже має SHA-256 кожного файла.
Тому мітка й негативні тести НЕ означають повного захисту від довільної корупції.

## Перевірка цілісності перед виконанням

У фізичному форматі оригінальної F3 **немає вбудованої CRC або підпису**:
довільний змінений байт іноді може означати іншу допустиму програму.
Для перенесених файлів потрібно отримати **довірений SHA-256 із незалежного
маніфесту або підписаного джерела**, а потім перевірити *фізичні байти*
перед декодуванням чи виконанням.

У чинному sens-trit додано два явні безпечніші маршрути:

~~~sh
target/release/sens-trit verify-f3-sha256 /tmp/short.senc 19b495e17cd0522c1af4863704b92751df5e5769ee0bfe3c9844aedbc0a57406
target/release/sens-trit eval-f3-sha256 /tmp/short.senc 19b495e17cd0522c1af4863704b92751df5e5769ee0bfe3c9844aedbc0a57406
~~~

Цей конкретний відбиток відповідає **лише** зразку 3 фізичних байтів
f3 40 60. Для інших програм очікуваний хеш треба отримати з
верифікованого manifest, не копіювати з прикладу. CLI читає файл **один раз**,
перевіряє 64 нижньорегістрових шістнадцяткових знаки та фізичний SHA-256 і
лише після успішного порівняння викликає оригінальний canonical F3 decoder
та T5 evaluator. При невідповідності **нічого не виконується**.

Важливо: SHA-256 **сам собою не доводить автора** файла. Якщо нападник може
міняти одночасно файл і очікуваний хеш, потрібен підписаний/довірений канал
публікації manifest. Незахищені старі eval-f3 / open-f3 залишаються
явними режимами для локальних довірених файлів.

[Перевірка справжніх байтів і негативних SHA мутантів](https://github.com/juv4uk/sens/actions/runs/38172651013)
на GitHub пройшла успішно; наступний тест охоплює всі 9 F3 файлів
разом із sha256 їхніх staged manifest.

## Що означає «один байт»

Існуючий `research/framed3/fixtures/car-cons-one-nil.f3m` — справді **один байт `0x3E`** у чинному dense F3M-1, який відновлює точні слова `10 100 10 111 1 000 01 01` і виконується тим самим SENS evaluator як `CAR(CONS(1,NIL))`. Отже це **реальне фізичне кодування виконуваної SENS-програми**, а не інша мова або лише абстрактний rank-доказ.

Водночас це **не** самодостатній F3C `.senc`: F3M не містить внутрішнього
selector/version/checksum. Сімейство відоме з явного `.f3m` маршруту, а
**профіль визначає довжина payload**, не sniffing вмісту. Чинний F3M-1
використовує всі **256/256** байтових кодів; F3M-2 — наступні **65 536**,
F3M-3 — наступні **16 777 216** global ranks, F3M-4 — наступні
**4 294 967 296**. Для F3M-3 вже доведено реальні COND-виконання,
найраніший 6/6-capability witness `16 3C 63` і exhaustive final-64K winner
`FF FB 37`. Для F3M-4 є algebraic capacity proof, 65 536 stratified
roundtrip samples і executable `DE AD BE EF`. Повні evaluator sweeps 16M/2^32
лишаються окремими proof gates. Sparse 45/256 mapping — лише історичний доказ.

## Умови допуску F3 у production

1. Одна й та сама точна мова з обома кодеками; жодних «псевдооператорів» або зміни арності, `QUOTE` дані залишаються даними; `((0))` не рекламувати як виконувану програму.
2. Explicit caller/extension codec selection, `0xf3` маркер F3; без content sniffing, без неявного fallback та без одночасного T5/F3 трактування одного файла.
3. Canonical Rust D2/physical T5 oracle + незалежний reference decoder F3; **паритет фізичного носія та незалежний обмежений семантичний допуск D3** успішно розділено і перевірено в [CI #38169848649](https://github.com/juv4uk/sens/actions/runs/38169848649): 1703 записи, 2229 фізичних перевірок, 6 D3 admitted, 551 D3 rejected, 31 негативний тест, 0 failures. Це НЕ доказ повної семантики D1–D9.
4. Тільки real physical bytes включно з F3-маркером; підбір F3 лише в короткій області; більший/непідтримуваний F3 не шкодить загальному режиму.
5. Малий декодер без надмірних алокацій та непропорційних обчислень; оновити CLI й безпекові guards тільки після двох оракулів, окремої fail-closed межі й зеленого CI.
6. Нових Git-гілок не створювати; один production Rust-власник [#5439](https://github.com/juv4uk/sens/issues/5439) та інтегратор [#5041](https://github.com/juv4uk/sens/issues/5041).

**Метод:** короткий формат націлюється не на абсолютний показник стиснення будь-якого файла, а на найкоротший *фізично валідний* носій у двох зафіксованих режимах. Цей принцип узгоджується з ідеєю deterministic minimal representation, наприклад [RFC 8949 §4.2](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2), але конкретні біти SENS визначають лише наші власні перевірки.
