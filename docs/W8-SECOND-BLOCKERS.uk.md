# Другий блокер після історичного W8: не вибирати legacy наосліп

Канонічний SENS за замовчуванням **правильно** блокує неоднозначне
8-бітне слово: історичний SID8 і теперішній D8 можуть мати ті самі біти.
У `scripts/audit_w8_source_era.py` ми вже довели, що 197 зі 226
оригінальних W8-блокувань мають **ті самі байти** у Git-знімку
30 вересня 2026. Це хронологія, не семантична тотожність.

## Новий експеримент без публікації

```bash
python3 scripts/triage_w8_legacy_successors.py \
  --repo . --out /tmp/sens-w8-next-barriers.json
```

Скрипт використовує наявний незмінний Git-аудит і канонічний
`migrate-three-pass.py`, який запускається **лише --dry-run**,
`--source-era legacy --unpaired-only`, у тимчасовій папці. Він
порівнює дві незалежні таблиці за точним шляхом і поточним Git blob SHA
лише для 197 файлів із підтвердженими історичними байтами.
Для кожного видно, який **наступний** код, недвійкове слово, структурний
контроль D2 чи невідома семантика блокує переклад після припущення
історичної ери.

- `UNMAPPED_LEGACY_SID8:XXXXXXXX`: потрібен ратифікований наступник
  старої функції, наприклад робота агента #4577.
- `NON_BINARY_OR_UNTYPED:wordN`: потрібний точний закон числа,
  тексту, локального імені або поділ програма/дані.
- `BINDING_UNPROVED`, `D2_STRUCTURE_UNPROVED`, `HOST_EFFECT_UNPROVED`:
  окремі семантичні закони, які не можна замінювати транспортацією.
- `MECHANICAL_CANDIDATE_ONLY`: парсер може створити байти, але
  незалежної еквівалентності історичного та нового виконання **немає**.

Звіт детерміновано групує наступні перешкоди за конкретними бітами та
позицією слова. GitHub Actions зберігає **всі** шляхи, SHA та причини
у JSON, показує найбільші групи в Summary.

**Заборони не змінені:** скрипт не пише жодного `.sens`, не переписує
`.lisp`, не вибирає `legacy` як типовий або дозволений режим для
реальної міграції, не сертифікує програму як виконувану та не змінює
жодного ратифікованого домену.

## Використання агентами

Один агент бере конкретний `UNMAPPED_LEGACY_SID8` із його SHA-прикладами,
звіряє історичний реєстр і ратифікований поточний resident. Інший
розв'язує `NON_BINARY_OR_UNTYPED` без підміни даних викликами.
Після внесення спільного доведеного закону повторюється цей **самий
повний** прогін, і вимірюється перехід до наступного блокування або
суто механічної готовності.

Реальний прийнятий перенос оригінальної виконуваної програми окремо
потребує доказу семантичної еквівалентності, поточного оракула,
фізичного T5, Rust D2 та перевірки в PR. Сам по собі цей експеримент
не дає жодного успішно мігрованого файла.


## SHA-перевірений поділ за типом джерела

Результат другого блокера тепер **звіряється ще й з уже чинним** реєстром
`scripts/report_original_migration_candidates.py`, не з окремими новими
припущеннями. Кожне з 197 джерел мусить мати однакові шлях і Git blob SHA
в історичному W8-списку та в чинному реєстрі. Інакше вся діагностика
відхиляється.

`NONPROGRAM_DATA_REVIEWED` приймається лише за чинним окремим
маніфестом власника, який підтверджує той самий SHA. Для
`ARCHIVED_BENCHMARK_NONPROGRAM` додатково діє точний історичний
закон шляху, а не довільна назва директорії. Решта лишається
`UNCLASSIFIED_NEEDS_SOURCE_PROOF` — це **не твердження, що файл виконуваний**.

У JSON збережено повні первинні результати `next_barrier_cohorts`,
а `source_scope_next_barrier_cohorts` відокремлює дві черги:

- `DATA_CONTRACT_NO_EXECUTABLE_T5` — тільки збереження/опис даних,
  не створювати виконуваний `.sens`.
- `EXECUTABLE_OR_UNCLASSIFIED_NEEDS_ORACLE` — дослідити точний старий
  виклик, ратифіковану сучасну функцію, D2, фактичне виконання фізичного
  T5 та **незалежний оракул**.

Повна перевірка рахунків гарантує, що ніхто не губить оригіналів між
цими двома чергами й не змінює загальне число 197 історично однакових
Git blobs. Агенти мають брати **другу чергу** для семантичної міграції;
перша не може покращувати метрику мігрованих виконуваних програм.
