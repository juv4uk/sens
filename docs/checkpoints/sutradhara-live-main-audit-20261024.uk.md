### Підтверджений обсяг і борги

- D1–D5 мають ратифіковані каталоги й низку виконуваних законів; ратифікація коду/адреси сама по собі не доводить викличність кожної функції.
- Окремий аудит поверхні D1–D11 на коміті [`62ddd1bb`](https://github.com/juv4uk/sens/commit/62ddd1bbf558f8ca6943758214b073f89c571b54) класифікував 2 558 поверхонь: 1 219 живих під власним ім'ям, 22 примітиви, 1 альтернативне ім'я, 520 композицій/селекторів, 364 відкладені, 432 не визначені, 0 доведено відсутніх. Це класифікація поверхонь, не результат наскрізного виконання.
- `knowledge/d6-mechanism-ledger.json` має 64 координати D6, але лише **4/64** механізмів з доказовим статусом: 1 `DIRECT_LAW`, 3 `LOWER_DOMAIN_COMPOSITION`, 0 `LISP_OWNED`, **60 `MISSING`**. D6 LENGTH (`000000`) поки не має допущеного прямого runtime-механізму. Не оголошувати весь D6 готовим.
- D12 — окремий точний знаковий числовий домен, не домен функціональних opcode. D12-арифметика і фізичні свідки вже додані раніше; звичайний source/REPL шлях лишається D24-first для Core4-сумісності, а цільовий math/T5M профіль допускає явний D12 мінімум.
- Загальна ціль повної виконуваності D1–D12+ і готовність до релізу залишаються **NO-GO**, доки всі потрібні резиденти не отримають семантичний контракт, реалізацію і позитивний/негативний фізичний доказ.

## Наступний порядок роботи

1. Дочекатися фактичного завершення runs 40103934731, 40103896377, 40103880266, 40103784085 через перевірку GitHub, а не внутрішню симуляцію. Виписати перший RED із точним ID, шаром, командою/діагностикою та SHA.
2. Виправляти тільки першопричину кожного актуального RED. Позитивний закон має повертати точний D1-результат; мутант — точне протилежне D1; некоректна структура — очікуваний Type. Не перетворювати Type на `ні` та не послаблювати сторожів.
3. Для кожного SENS-свідка перевірити прямий запуск, T5M mint/open/verify, paired execution і standalone execution. Де потрібен Core4, подавати явний профіль тільки для цього свідка; не додавати прихованих fallback-ів.
4. Після стабілізації D11 продовжити найменший доказовий доменний крок: D6 LENGTH (`000000`) і наступні D6-координати. Спочатку перевірити ратифікований закон і точні нижчі залежності D3/D4/D5; після Lisp-композиції окремо довести, що відповідна D6-ідентичність справді допущена runtime-ом. Не підміняти D6 функцію звичайним D24 числом, D7 текстом або неявним псевдонімом.
5. Оновлювати `knowledge/d6-mechanism-ledger.json` лише коли є відтворюваний доказ; для кожного резидента фіксувати точні координату, статус, джерело і негативний контроль проти сусіднього домену.
6. Перевіряти всі вже змінені Lisp-файли через наявний фізичний workflow і актуальні бенчмарки. Benchmarks вимірюють механізм; вони не замінюють семантичних законів.
