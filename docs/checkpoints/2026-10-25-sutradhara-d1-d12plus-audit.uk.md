## Що реально знайдено у вихідному SENS

У `lib/core4.lisp` вже є похідні визначення `відобразити` (MAP), `відсіяти` (FILTER), `згорнути` (REDUCE), `SCAN`, NTH/MAPLIST та інші рекурсивні композиції. COMPOSE/FLIP/CURRY визначені як SENS-замикання. Це не слід повторно генерувати під іншими іменами.

У `scripts/prove-lisp-semantic-t5m.sh` уже зареєстровані SENS-свідки з позитивними, мутантними та/або Type-негативними гілками для D6 FILTER, MAP-ONTO, REDUCE, SCAN, NTH, MAPLIST, COMPOSE/FLIP та пов'язаних законів. Runner передбачає реальний маршрут SENS → Zig/T5M → SENS; наявність реєстрації сама по собі не засвідчує PASS на новому SHA.

`knowledge/d6-mechanism-ledger.json` наразі описує 4/64 механізми (DIRECT_LAW=1, LOWER_DOMAIN_COMPOSITION=3, MISSING=60), але його власне поле `authority` досі посилається на Contract 11.8. Окремий `knowledge/d6-mechanism-census.json` посилається на Contract 11.5 і має інші лічильники. Ці файли не можна механічно об'єднувати або вважати актуальним Contract 12.0 без переаудиту рядків, доказів і правил статусів. Не позначати SENS-замикання як прямий runtime-механізм лише тому, що функція визначена у бібліотеці.

Попередній hosted run `40160350429` стосувався SHA `21505ad2541d5be6135ed84fc33697146cf75b8e`, а не поточного знімка. У тому ж run окремий набір мовних законів звітував 508/508, але це не робило весь workflow зеленим.

Поточний commit `6c8d1e3e8463185800dab861ec93e3008d67263d` змінює саме SENS-маркування форматів у `lib/lisp-fs.lisp` через явні канонічні конструктори й додає перевірки READ/WRITE у `tests/fixtures/wsm-fs-record-producer.lisp`. Його metadata все ще каже `NATIVE_SENS=PENDING_CI`. Отже, старий RED не переноситься автоматично на новий SHA, але виправлення ще й не можна назвати доведеним до повторного фізичного запуску.

## Рішення й наступний порядок робіт

1. **P0 — поточний SHA F6.** На `main` після `6c8d1e3e8463185800dab861ec93e3008d67263d` виконати `cargo test -p sens-cli --test wsm_fs_f6_pipeline` та канонічні фізичні SENS/Zig/T5M-перевірки, які визначені наявним CI/runner. Зберегти фактичні stdout/stderr, source/physical SHA-256, exact D1-вердикт і workflow run ID. Перевірити round-trip `WRITE → READ` для обох фіксованих маркерів та відхилення чужого маркера. Не послаблювати валідатор заради зеленого тесту.
2. **P1 — відновити єдину доказову картину D6.** Переаудитувати `knowledge/d6-mechanism-ledger.json` і `knowledge/d6-mechanism-census.json` за Contract 12.0. Для кожного з 64 рядків окремо зафіксувати: ратифікованість, SENS-визначення, прямий механізм, фізичну проєкцію, позитивний закон, мутант/Type-негатив і точний SHA. Перегенерувати лічильники з джерел; не редагувати їх для бажаної статистики.
3. **P2 — наступний вузький функціональний крок: D6:101000 MAP.** Після P0/P1 визначити, чи існує прямий механізм виклику саме цієї координати. Якщо його немає — реалізувати за чинним контрактом, зберігши семантику SENS; доказати один виклик callback на елемент, порядок виходу, порожній список, неправильний D3-хвіст і відмову для того самого packed payload в чужому домені. Не плутати цей механізм із бібліотечним `відобразити` або `відобразити-до`.
4. **P3 — D10/D11.** Поелементно продовжувати аудит кожного функціонального резидента D10 за чинними бітами, спершу повторно використовуючи чинні SENS-композиції. Кандидати D11 документувати окремо від ратифікованого пулу; для кожного бракувати «заглушку» лише після перевірки джерела, runner і фактичного виконання.
5. **Рішення релізу.** Лише успішний фізичний маршрут на конкретному SHA та окреме рішення власника можуть перевести реліз із `NO-GO`. Статичний баланс дужок, визначення у файлі, ратифікована адреса або порожній CI-status не є нативним PASS.
