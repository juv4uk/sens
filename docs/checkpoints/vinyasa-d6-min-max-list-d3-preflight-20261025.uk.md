# Vinyāsa · D6 MIN-LIST/MAX-LIST · контрольна точка 25.10.2026

## Походження і місце у драбині

- Базовий `main` перед створенням об'єктів: `a75848f82c0e69b45de32ec0f74eb9b45b55f6a7`.
- Колезі Sūtradhāra подяка за D6:000000 LENGTH та D6:000001 LENGTH-ONTO у `f21698c08182f9349043b51fe53cb681e054cc72`.
- Ратифіковані координати: D6:000010 `найменше-у-списку` (`śreṇī-alpatara`, MIN-LIST); D6:000011 `найбільше-у-списку` (`śreṇī-brhattara`, MAX-LIST).
- D1 — предикат, D2 — граматика читача, D3 — CONS/CAR/CDR/EQ/ATOM, D4 — NULL/COND/LAMBDA/DEFINE, D5 — LESSP/GREATERP, D6 — композиція; D7 — текст, не виконуваний оператор.
- D10: 1024 ратифікованих ідентичностей не означають 1024 нативних механізмів. D11 містить бібліотечні кандидати. D12 — числовий домен.

## Фактичний дефект та мовне виправлення

У `lib/core4.lisp` чотири DEFINE MIN-LIST/MAX-LIST могли читати числові значення до перевірки пізнього неправильного D1 хвоста. Це призводило до пріоритету числової Type над структурною або до пізньої Type після вже виконаних порівнянь. Неправильний D1 хвіст є порушенням D3 списку.

Визначено `перевірити-структуру-списку-екстремумів`: прохід усіма `решта`, приймає лише структурне D3 `()`; для іншого атома породжує власну D3 CAR Type. Публічні `найменше-у-списку` і `найбільше-у-списку` виконують preflight до порівнянь. Збережено порожній результат `()` та вибір першого екстремуму при рівності. Обидва ядра викликають `менше?` або `більше?` тільки один раз на крок, а одноелементний випадок змушує D5 порівняння числа з самим собою, щоб не пропустити нечисловий атом.

Це композиції власної мови SENS, не нові коди та не розширення семантики Rust/Zig. Логіка не перетворює D1:ні на D3:().

## Фізичні свідки та чесний стан

Наявний `scripts/prove-lisp-semantic-t5m.sh` доповнено 6 сценаріями:
позитивний, мутант, D1 root, отруєний неправильний пізній хвіст
MIN-LIST, неправильний пізній хвіст MAX-LIST, нечисловий
одиночний MAX-LIST. Негативи відокремлюють D3 CAR Type від D5 Type.
SHA256 входів формує shell лише як транспортну квитанцію; мовний
вирок встановлює SENS.

**STATIC_FORM_BALANCE=PASS** для нових законів і DEFINE;
**NATIVE_SENS=NOT_VERIFIED**;
**ZIG_T5M=NOT_VERIFIED**;
**PHYSICAL_CORE4_VIEW=REQUIRES_CANONICAL_REMINT**;
**RELEASE=NO-GO**.

`knowledge/d6-mechanism-ledger.json` попередньо відмічає
D6:000010/000011 як MISSING за runtime-допуском. SENS DEFINE
не змінює цей доказ і не дозволяє вручну назвати їх CALLABLE.
