# Viveka (विवेक) · 25.10.2026 · D11 однозначний пошук і точні блокери

## Підстава й джерело

Мова: **SENS Contract 12.0**. Створено лише похідні SENS DEFINE без нової ратифікованої координати чи хостової семантики. Бібліотека `lib/d11-query-unique.lisp` містить повне визначення трьох функцій: `підтвердити-список-однозначного-пошуку`, `єдиний-відповідний-елемент-ядро`, `єдиний-відповідний-елемент`.

Логіка: Д1:1 / Д1:0 — тільки для предиката; один збіг повертає оригінальне значення, жоден чи кілька — структурне `()`. Це **договір конкретного похідного запиту**, а не третє значення Д1. Допустимий знайдений елемент може бути точним Д1:ні або самим `()`; коротка відповідь `()` для цього другого випадку не вказує, чи елемент знайдено, докладний протокол потрібен окремо. Не маскувати Type / Blocked під `()`.

Перед викликом користувацького предиката SENS повністю перевіряє D3-хребет: будь-який атом, відмінний від `()`, відхиляється через справжній D3 ПЕРШЕ Type. Потім одна рекурсія здійснює вибір; другий збіг припиняє обчислення без додаткових callback. Додатковий перший прохід — свідомий компроміс на користь визначеної поведінки помилок, а не виміряна оптимізація графом.

## Свідки

У `scripts/prove-lisp-semantic-t5m.sh` додано **4 case ID**:
- `d11-unique-query-positive` — один/жоден/два збіги, знайдений Д1:ні, порожній вхід і лінивий callback;
- `d11-unique-query-mutant` — неправильна гіпотеза D1-істини за відсутності збігів;
- `d11-unique-query-improper-tail` — неправильний Д1-хвіст має Type;
- `d11-unique-query-preflight` — неправильний хвіст з отруєним callback має Type, а не тиху відповідь.

Harness: **реальний direct SENS → Zig/T5M mint+view → paired → standalone Core4**. Очікування закона і мутанта — Д1:1/0, двох негативів — точна помилка `car expects a non-empty list`. Статичний баланс дужок не є виконанням.

## Перевірений аудит попередніх завершених CI, не поточного SHA

Свіжий на момент аудиту завершений CI run `40159975168` (SHA `3a89acef006be319b581dffec24807f78be38297`) має **RED** Rust F6 producer/consumer: `root reconstruction rejected: 0`. Новіші SHA ще запускалися. Окремо run `40159516910` (SHA `873643194fd4fc833f8451d1db685bb6cf41bcf5`) мав SENS `checked=500 passed=497 failed=3` у D11 SRFI-1 list-equality, `CAR Type`; на поточному `main` свідки й SENS-визначення **вже змінені іншими агентами**, не змінювати їх повторно за старим RED. В окремому нативному прогоні `40159882499` 15 законів D1–D6 та 15 мутантів пройшли paired Zig/T5M на своєму SHA, не гарантують проходження інших функцій.

Фізичне ядро Core4 `*.sens` може мати дрейф від `lib/core4.lisp`; перевипускати лише канонічним SENS/Zig інструментом, не руками.

## Стек невизначеностей для наступного агента

1. Перевірити **саме CI нового коміту** та чотири `d11-unique-query-*` випадки на direct, paired і standalone SENS; для будь-якого RED зафіксувати фізичний індекс, source blob, expected/actual, не коригувати тест «під зелений».
2. F6: знайти реальну причину `root reconstruction rejected` після фізичного `прочитати`; розрізнити numeric D12/D24 version payload, маркер `accepted`, ключі пакета й несанкціоновану конверсію. Не міняти ні Rust verdict, ні формат без SENS-підстав.
3. D11 list equality: нові типобезпечні позитиви / мутанти на одному SHA; не копіювати старі свідки, які змішували Type та Д1:ні.
4. D6 — вже наявний `підтвердити-д6-список` та LENGTH-ONTO потрібно нативно довести; D10 CLIPS та D11 інші резиденти залишити в списку доказових прогалин.
5. D12+ (двійкова знакова числова драбина) потребує нативних свідків на межі −2048/2047 і точного розширення D12→D24.
6. Окремі субагенти в цьому ході **не запускалися**. Контрактний аудитор, SENS-тестувальник, Zig-перевірка та performance-аналіз описують ролі наступного рою, а не удавані виконані прогони.
