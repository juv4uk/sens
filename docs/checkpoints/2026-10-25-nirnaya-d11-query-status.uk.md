# Nirṇaya (निर्णय) · 25.10.2026 · D11: пояснення однозначного пошуку

## Рішення

Контракт SENS 12.0: простий результат (один елемент або D3:000) лишається незмінним. Нова **похідна** функція `стан-однозначного-пошуку` повертає рівно одну з трьох структур:
- `(єдиний значення)` — один збіг, навіть коли `значення` дорівнює `()` або точному D1:ні;
- `(немає)` — жодного збігу **у перевіреному закритому списку**, а не глобальне заперечення існування;
- `(кілька)` — щонайменше два збіги, перший збіг не можна проголосити єдиним.

Це дані похідного протоколу, **не D11 примітив, не новий біт D1 і не нові ратифіковані координати**. Справжня помилка Type ніколи не маскується під `(немає)`; D1 ні не дорівнює D3 (). Початковий скінченний список перевіряється повністю перед викликом предиката. Результат з причинним маркером створюється тільки якщо користувач викликає додаткову функцію; звичайний `єдиний-відповідний-елемент` не змінений.

## Власні свідки

Додано до наявного `scripts/prove-lisp-semantic-t5m.sh`:
1. `d11-query-status-positive` — п'ять законів в одній SENS-формі, зокрема однозначний `()`, однозначний Д1:ні, 0 і 2+ збігів та лінивий предикат на порожньому вході.
2. `d11-query-status-mutant` — фальшиве твердження «2 = 1» мусить дати Д1:ні.
3. `d11-query-status-improper` — неправильний хвіст з Д1:ні мусить дати D3 CAR Type.
4. `d11-query-status-preflight` — помилка в структурі має передувати виклику отруєного предиката.

Тільки SENS обчислює результати; встановлений harness робить direct, нативний SENS/Zig T5M mint+open+verify, paired і standalone Core4, з негативними перевірками exact Type.

3. D6 UNION: підтвердити існуючий новий шлях `lib/core4-parts/core4-d6[ b].lisp` і exact Type позитиви/негативи, не підміняти джерело контракту.
4. D11 SRFI-1 LIST= та F6 залишаються незалежними; кожна помилка повинна мати свою source/physical квитанцію.
