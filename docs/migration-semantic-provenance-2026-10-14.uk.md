# SENS · хронологія семантичних меж для міграційного рою

**Дата звірки:** 2026-10-14. **Статус:** інженерний handoff / provenance, **не** нова мовна аксіома, не контракт і не дозвіл на callability.  
**Координація:** [#5029](https://github.com/juv4uk/sens/issues/5029), [#5041](https://github.com/juv4uk/sens/issues/5041).  
**Чинне право рішення:** власник SENS, [AGENTS.md](../AGENTS.md) і ратифіковані машинні контракти. Історичний коміт доводить, *коли код з'явився*, але сам по собі не ратифікує його сучасного значення.

Цей запис дає агентам одну відтворювану карту, щоб не переносити в чинну драбину припущення зі старих епох. Не використовувати його як другий регістр координат чи CI gate. За суперечності звіряти найновіше явне власницьке рішення і чинний ратифікований машинний контракт; записати конкретний SHA, не вигадувати відповідник.

### Точність часової атрибуції

- **Дата появи/редагування файла**: коміт із Git-історії.
- **Дата рішення власника**: окрема ратифікація issue/контракт; її не виводять із віку файла чи коментаря.
- **Чинна координата**: тільки за поточним ратифікованим джерелом.
- **Чинний механізм**: доказ допуску/виконання незалежно від факту резидентності.
- **Фізичний носій**: T5/F3C/ABI перевіряють exact bits/length/canonical bytes, не вирішують SENS-семантику.

## 2. Як перед зміною читати історію конкретного файла

Запускати з чистої актуальної копії **цього** репозиторію, перед редагуванням власного неперетинного write-set. Підставити реальний шлях і записати повернені SHA; ці команди **не редагують робочі вихідні файли**. `git fetch` при цьому оновлює локальні Git refs та об'єкти:

```bash
git fetch origin main
git status --short
git rev-parse HEAD
git rev-parse origin/main
FILE=crates/sens/src/ternary_transport.rs
git log origin/main --follow --date=iso-strict --format='%H %aI %cI %s' -- "$FILE"
git log origin/main --follow --name-status -- "$FILE"
git log origin/main -S'encode_ternary_coordinates' --format='%H %aI %s' -- "$FILE"
git log origin/main -G'DomainCoordinate|UnsupportedDomainWidth' --format='%H %aI %s' -- "$FILE"
git blame origin/main -- "$FILE"
git show <VERIFIED_SHA>:"$FILE"
```

`-S` перевіряє зміну кількості точних входжень, `-G` шукає зміну рядків за regex; обидва — **підказки до читання дифів**, не гарантія першого семантичного переходу. `git blame` показує останнього редактора рядка, не автора закону. `--follow` працює з одним шляхом і шукає перейменування; для зміни сенсу всередині багатьох файлів потрібні також issue, контракт і сусідні коміти. Author date (%aI) та committer date (%cI) можуть відрізнятися.

Перевірити конкретний акт і його місце в поточній історії:

```bash
git show --format=fuller --stat cf7011418d1daf583ce7cdfe78f16af74ef66e2c
git show cf7011418d1daf583ce7cdfe78f16af74ef66e2c:contracts/d8-ratification.lisp
git merge-base --is-ancestor cf7011418d1daf583ce7cdfe78f16af74ef66e2c origin/main
```

Остання команда з кодом 0 підтверджує ancestry, з іншим кодом — вимагає окремо дослідити інтеграцію; **не** трактувати неналежність до ancestry як семантичний фальсифікатор. Не запускати довільний історичний код лише для перевірки старої гіпотези на сучасному CI.

## 3. Рішення мігратора на одному конкретному виклику

1. Зафіксувати **stem, точний старий source SHA та історичний контекст**; історичні SID8/імена зберегти лише як provenance **поза Zig**.
2. Знайти чинну ратифіковану `(domain, exact_width, exact_bits, law)` форму. Не будувати відповідність за однаковим payload, написанням чи 8-бітною довжиною. Немає допущеної відповідності — **не змінювати саме цю форму**, але інші незалежні форми мігрувати.
3. Якщо це **D7 дані**, для **нової міграції** відразу використовувати чинну ратифіковану D7 keyboard v2 (128/128), з точними 7-бітними координатами. **Власник підтвердив, що за історичним D7 v1 (126/128) жодної програми або даних не мігрували** ([уточнення в #5029](https://github.com/juv4uk/sens/issues/5029#issuecomment-6169008807)). Тому **не вимагати v1→v2 конвертера, маніфесту чи CI-гейта** як умови роботи рою. D7 v1 лишається лише історичною provenance; якщо колись буде виявлено реальний окремо SHA-підтверджений v1 payload, спершу довести його формат і лише для нього обґрунтувати явне версійне перетворення, без зміни основного маршруту. D7-цифри не перетворювати автоматично на D24+.
4. Розділити **резидентність**, **callability**, **виконуваний закон** і **transport admission**. D10 координата через Zig `decodeCoordinates` — не виконуваний виклик; звичайний T5 `decode` має власний профіль ≤D9. D11 не розширювати самовільно, доки працює окремий відповідальний агент.
5. Створити дозволені проєкції одного stem: `name.lisp` (канонічна `ук` поверхня), `name.sens` (фізичний T5 exact-width), `name` (генерований безрозширеневий `0/1` view) — лише там, де достатньо доказів із [#4449](https://github.com/juv4uk/sens/issues/4449)/[#4455](https://github.com/juv4uk/sens/issues/4455).
6. Зберегти SHA трьох проєкцій і корпусу. Zig↔Rust byte-exact та decoded `(domain,width,payload)` parity — **окремо** від позитивного й однобітного негативного native SENS verdict. `encode(decode(bytes)) == bytes` свідчить про транспорт, не про правильне призначення функції.
7. Віддати в #5029 короткий `CLAIM/READY`: реальний виконавець, базовий і новий SHA, точні файли, історичний commit/owner authority, позитивний+негативний test id і команду відтворення, результат на точному SHA; `UNVERIFIED` там, де запуску не було. Для перетинних файлів — HANDOFF/ACK. Важливі семантичні рішення — лише за власником.

**Окремий принцип фізичної цілісності:** канонічний T5 може залишитися канонічним і після втрати байта (приклад `D9:100000000 → 51 02`; усічене `51` інтерпретується як `D5:10000`). Тому перевірка очікуваної довжини + зовнішнього SHA потрібна для файлів і корпусів; не придумувати глобального «кожне усічення T5 відхиляється» — такого закону немає.

## 4. Межі відповідальності рою

- **[#5141](https://github.com/juv4uk/sens/issues/5141), [#5609](https://github.com/juv4uk/sens/issues/5609):** джерело → AST → доведена координата та закон, без фізичного переозначення T5.
- **[#5767](https://github.com/juv4uk/sens/issues/5767), [#5770](https://github.com/juv4uk/sens/issues/5770):** фізичні Zig/Rust T5/ABI parity, точна ширина, канонічність, негативи; без нормативної семантики Zig або Rust.
- **[#5771](https://github.com/juv4uk/sens/issues/5771):** matched benchmarks після байтової рівності, не підміна логічного закону швидкодією.
- **[#5608](https://github.com/juv4uk/sens/issues/5608):** прибрати анахронічний історичний SID8↔D8 нормативний oracle, але зберегти справжні чинні негативні тести.
- **[#5029](https://github.com/juv4uk/sens/issues/5029):** координувати write-set, походження, результати. Не вводити нових глобальних стопорів. Єдиний автоматичний CI — наявний `.github/workflows/ci.yml`, без додаткового автоматичного дубля.

Цей handoff **не змінює** `AGENTS.md`, контракти, функції, доменні координати, бібліотеки, тести чи workflow. Його можна використовувати незалежно від темпу інших агентів; останнє слово завжди за чинним SENS законом і явним власницьким рішенням.
