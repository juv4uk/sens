# #2000 — перший smoke масштабування без верхньої межі ширини

Лише дослідження. Жодної production-міграції carrier або семантики.

## Що перевірено

C-структури carrier не мають мовної максимальної ширини. Smoke перевіряв:

```text
64, 65, 128, 255, 256, 257, 1024, 4096 біт
```

`4096` — лише тестова точка.

Перед кожним вимірюванням перевірено:
- equality з точною шириною;
- нуль з однаковим числовим значенням на сусідніх ширинах залишається іншою identity;
- `append(bit)`, а потім `parent`, відновлює початкове слово;
- початкове слово лишається точним prefix свого appended child;
- інформація про leading width не втрачається.

Усі перевірки пройшли.

## Перший семантичний результат

Не виявлено semantic cliff на переходах:

```text
64 -> 65
255 -> 256 -> 257
1024 -> 4096
```

Small-inline+spill carrier фізично переходить у spill на 64->65, але закон identity не змінюється.

## Результат по allocation

Для heap/spilled append перша реалізація виділяє один новий payload на операцію:

```text
64   -> 9 bytes
128  -> 17 bytes
256  -> 33 bytes
1024 -> 129 bytes
4096 -> 513 bytes
```

Equality і prefix не роблять allocation у вимірюваному циклі.

## Інтерпретація

Перший важливий claim витримав:

> довші скінченні слова механічно дорожчі, але не переходять через семантичну межу ширини.

Наступне питання carrier не «чи треба заборонити довгі смисли?», а:

> яка chunked/bytewise representation зробить parent/prefix/append дешевшими?

## Наступний falsifier

Додати chunk-aware кандидат, який:
- порівнює вирівняні prefix-байти перед tail bits;
- робить append без перебудови всіх попередніх бітів;
- використовує sharing/copy chunks або amortized storage;
- зберігає точну ширину та leading zeros.

Якщо він прибере поточний O(width)-per-bit overhead зі збереженням усіх identity properties, current slope буде підтверджено як вартість prototype algorithm, а не закон мови.

Raw evidence: `docs/research/2000-unbounded-width.tsv`.
