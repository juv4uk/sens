## Що з цього справді «канонічна ідентичність» (source-confirmed, 4 місця)
1. `value.rs:564` — `(Value::String(l), Value::String(r)) => l == r`: рівність рядків = побайтова UTF-8, а не порівняння кодів Text7.
2. `syntax.rs:53` / `value.rs:494` — String як варіант AST і значення (`Rc<str>`).
3. `syntax.rs:120`, `syntax.rs:361` — теги fasl `3` і wire `0x55` серіалізують UTF-8 (`put_text`/`get_text`).
4. `eval/mod.rs:139` і `closures.rs:640` — літерал ↔ значення **без жодної нормалізації**, тобто перехід «людський текст → канонічний код» у рантаймі відсутній.

Єдине джерело нових String — `parser.rs:317`. Отже **точка входу для Text7 одна**: читач, який має відхиляти звук без клітинки UPC-7 (fail closed), як кодек у shiva-sutras#32.

## Що можна видалити без нової семантики (пропозиція, не перевірено)
- Нічого з 84 не можна прибрати ізольовано: String досі використовують `string-slice`, json, io, digest (33 сайти). Видалення починається з **читача + рівності + теги (12 сайтів)**, builtins слідом.
- 35 host-сайтів, схоже, лишаються людською межею (клас `human-boundary` за #1707), а не боргом.

## Чого не знаю (not-yet-verified)
- Скільки з 33 builtin-сайтів справді залежать від UTF-8 семантики (`string-slice` рахує Unicode scalar) проти простого проносу тексту.
- Скільки `.lisp`-фікстур містить літерали за межею таблиці UPC-7 (потрібен окремий скан, і він залежить від рішення по shiva-sutras#32).
- Чи `Value::String` десь використовується як ключ dispatch (потрібен окремий пошук `HashMap<Rc<str>`… уже за межею #1700).

## Крок 2: скан `.lisp`-літералів з кирилицею проти таблиці UPC-7 (з shiva-sutras#32)

Дані: `data/1700-uk-literals-vs-upc7.tsv`. Таблиця і кодек — **із чернетки #32** (не з main; SHA `8ce2339a…`, ще не запінено в sens). Скрипт у репо не закомічено.

**Межа методу (важливо):** літерали беруться регулярним виразом по рядках (`"…"` з екрануванням, коментарі `;` відкинуто), а до кодека йде лише **перший 60-символьний префікс** — тож «encodes» означає «префікс кодується», не «весь літерал». Багаторядкові рядки не обробляються. Лише літерали, що містять кирилицю (1279 із 18290 у 454 файлах); інші (`8651` поза алфавітом, латинські англ. повідомлення, `7921` «кодуються як SLP1» лише тому, що літери й пробіл збігаються з латинським SLP1) **не є свідоцтвом про санскрит і в цю статистику не входять**.

| результат | літералів |
|---|---:|
| префікс кодується (`uk`) | 617 (48%) |
| заблоковано: **велика кирилична літера** | 348 |
| заблоковано: латинська літера (змішаний текст) | 209 |
| заблоковано: комбінівний діакритик (IAST-подібна кирилиця) | 87 |
| заблоковано: пунктуація/інше | 12 |
| заблоковано: інша кирилиця | 5 |
| невизначено | 1 |

**Головні висновки (empirically confirmed на цій вибірці, з межею вище):**
1. **Регістр — найбільший пробіл: 348 із 662 блокувань.** Шар `uk` малолітерний; великі літери не мають клітинки й не мають правила (нормалізація регістру не дозволена без рішення: SLP1 регістрочутливий, `K`≠`k`). Це **нове питання власнику, яке не піднімалось у #31**.
2. 209 блокувань — змішаний текст «українська + англійські імена» (`oracle-check`, `.lisp`); Text7 не може бути «цілим текстом» повідомлення, лише його українською частиною.
3. 87 — санскрит кирилицею з комбінівними діакритиками (`knowledge/sanskrit-cyrillic-*.lisp`): це окремий layout, не `uk`.
4. Після #32 звуки без клітинки (`UnassignedSpelling`) у вибірці — **0**: розміщення покриває все, що трапляється як українські **малі** літери.

**Наслідок для читача (`parser.rs:317`):** «відхиляти літерал зі звуком поза UPC-7» відхилив би зараз ~52% кириличних літералів у репо — переважно через регістр і змішаний текст, а не через нестачу клітинок. Отже fail-closed на читанні неможливий без окремого рішення про регістр і про змішані/людські повідомлення (host-boundary).
