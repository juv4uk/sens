# Дизайн: чесний runtime-бенчмарк SENS проти CPython

**Статус:** базовий план нижче є історичним і був виправлений за прямою
вказівкою власника 2026-10-17. Чинний метод — фізичний T5 source-to-result
проти Python `.py` source з повним часом процесу; див. результат
[`physical/runs/20261017T053621Z/README.uk.md`](../../benchmarks/cross-language/sens-vs-python/physical/runs/20261017T053621Z/README.uk.md).

## Мета

Поточна практична мета — виміряти один підтверджений поточним production
шляхом фізичний T5 workload проти ідентичного Python source workload. Це
дослід конкретних рушіїв end-to-end; він не є оцінкою чистого CPU execution
або загальним рейтингом мов. Повна ціль 3–5 стандартних алгоритмів лишається
відкритою до появи підтверджених фізичних SENS-програм із семантичним parity.

Виміряти час виконання й пам’ять конкретних еквівалентних програм SENS та CPython на одному середовищі. Результат має відповідати на питання про ці реалізації, workload’и й параметри — не ранжувати мови взагалі.

## Межі й опори

- Розширити наявний міжмовний стенд `benchmarks/cross-language/`; не створювати дубль загального harness або нового автоматичного workflow.
- Поточний `benchmarks/cross-language/run.py` і його результати — історичний донор Function8/FASL. Їх не можна повторно називати сучасним SENS-vs-Python доказом.
- SENS-варіант має виконувати актуальну програму SENS через чинний production reader/evaluator, не історичний Function8/FASL і не окрему копію семантики в Rust. CPython-варіант запускається з `.py` source у звичайному CPython, без попередньо згенерованого `.pyc`.
- Основна метрика — steady-state виклик уже завантаженої програми. Процесний startup, читання/розбір source, підготовка середовища й correctness перевірки відбуваються поза вимірюваною секцією. Їх можна записувати окремо, але не додавати до CPU-bound часу.

## Початкові workload-кандидати

Перевірити готовність трьох зрізів; жоден не потрапляє в таблицю часу до семантичного parity:

1. **`binary-trees`** — стандартний алгоритм з алокацією дерев; початковий параметр `N=10`, еталон — чинний fixture `benchmarks/standard/binary-trees/expected-n10.txt`.
2. **Рекурсивне ціле обчислення** — кандидат `fib` із наявного міжмовного набору; параметр і визначення мають збігатися в обох реалізаціях.
3. **JSON parse/serialize** — той самий зафіксований документ; порівнювати результат структури та канонічне серіалізоване представлення. Звіт мусить вказати, що саме SENS `json-parse` може делегувати host-механізму, а Python використовує стандартний модуль `json`.

Кожен кандидат спершу проходить окремий smoke/parity gate на поточній гілці `main`. Якщо SENS не може виконати workload через відсутню мовну/reader/runtime спроможність, його позначити `BLOCKED` із конкретною помилкою; не підміняти його старим FASL, host-кодом під виглядом SENS або іншим алгоритмом. n-body/Mandelbrot не включати, доки обидві сторони не матимуть зіставної числової семантики; regex не включати, доки не буде однакового regex-контракту. Відсутній третій PASS означає, що загальна мета бенчмарку ще не досягнута.

## Вимірювання

- Одне середовище: одна ОС/WSL instance, фізичний CPU та affinity без конкурентного важкого workload; записати CPU, ОС/kernel, WSL/Guix контекст, SENS Git SHA, SHA бінарника, версію Rust/toolchain, версію CPython і хеші джерел та input corpus.
- Для кожної пари `workload × implementation`: новий процес, одноразове завантаження програми й setup; **10 warmup-викликів**, потім **100 окремо виміряних викликів** у тому самому прогрітому процесі. Кожний raw sample містить порядковий номер, `elapsed_ns`, workload/input SHA, implementation/source SHA і результат або його digest.
- Перед таймінгом незалежно перевірити очікуваний результат і точний паритет SENS↔Python. Розбіжність забороняє timing rows для цієї пари й створює явний `FAIL/BLOCKED` запис.
- Розрахувати median, p95 і p99 із 100 raw latency samples за наперед визначеним nearest-rank правилом. Позначити, що p99 на 100 samples — крайній порядковий елемент, а не сильна оцінка хвоста.
- RSS вимірювати у процесі окремо від часу: `VmRSS` після load/setup і після warmup як baseline, плюс `VmHWM` наприкінці як процесний пік; звітувати absolute peak і delta до baseline. Не називати цю delta лише пам’яттю workload’у — вона включає allocator/runtime ефекти.
- Зберігати 100 raw samples на кожну реалізацію/workload та environment/corpus manifest. Усі агрегати й графіки мають відтворюватися лише з цих raw файлів.

## Звіт і графіки

Створити український звіт із таблицею workload’ів, parity-статусом, `n`, median/p95/p99, RSS baseline/peak/delta, ratio CPython/SENS і exact provenance. Додати boxplot та histogram для кожного виміряного workload’у, з однаковою шкалою/одиницями для пари; жодних графіків для заблокованих замірів. Формат графіків — статичний SVG/PNG, що генерується збереженими raw data без мережевих залежностей.

Висновок має називати швидший варіант лише для конкретного workload’у й вказувати межі: одна машина, одна версія runtime, 100 samples, вибрані параметри, виміряні runtime/allocator шари. Не робити узагальнення «SENS швидший за Python» із трьох алгоритмів.

## Перевірки та критерії завершення

- Тести harness перевіряють порядок warmup/sample, статистичні значення на відомих наборах, fail-closed parity, незмінність raw schema та відтворення агрегатів/графіків.
- Перед реальним вимірюванням повторно виконати `wsm-agent bench-ready`; не запускати, якщо статус `BUSY`. Зафіксувати передзапусковий стан і запускати benchmark серійно, без паралельних CPU-heavy робіт.
- На кожному workload має бути або `PASS` parity + повний вимір, або точний `BLOCKED/FAIL` із першою помилкою. Загальна ціль `PASS` вимагає щонайменше трьох workload’ів із завершеним parity та raw measurements; інакше звіт є частковим і не заявляє переможця.
- Не змінювати мовну семантику SENS, її домени, CI-графік чи загальні правила branch/approval заради benchmark. Якщо робочий SENS execution path відсутній, фіксувати blocker і зупинити лише відповідний workload.
