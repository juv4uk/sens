## Аксіоми, які перевіряти на кожному кроці

- Доменна адреса і ширина первинні: D1:1 не дорівнює D2:01, D3:001 або D4:0001; leading zeros, QUOTE та D2 00/01/10/11 зберігати точно. Не переводити семантичні ідентичності через десятковий посередник.
- D3: 000 structural empty, 001 QUOTE, 010 ATOM, 011 CDR, 100 CAR, 101 EQ, 110 COND, 111 CONS. D1 має рівно YES/NO, D3 empty — не D1 false; двопольовий COND не змінювати без окремої ратифікації.
- D7 символи «0…9» — текст, не математика. При цитуванні спершу перевірити наявну ратифіковану координату об'єкта у власному домені, D7 — лише для непокритого тексту.
- D1–D10 — координати та закони; лише явно кваліфіковані D24/D48/D96/D192+ — математичні значення. Десяткове відображення для людини не стає внутрішнім оператором або ідентичністю.
- T5 може не виявити усічення, якщо коротший потік сам є канонічним: D9 100000000 => hex 51 02; префікс 51 => окрема D5 10000. Невіддільність усунення байта доводиться лише pinned expected byte length + SHA-256 із зовнішнього receipt, НЕ послабленням канонічного кодека.
- D10 у T5 coordinates — транспорт, не дозвіл на execute. D11 не розширювати мовчки: його окремий стан/агент визначає власник; Contract major #d11 не є дозволом додати ширину 11 до T5.
- У Zig не відтворювати історичні SID8/Sens8/Function8/W8 типи/диспетчери/порівняння як семантичну владу; provenance лишається в архівній Git-історії, поза активними gates.

### Рецепт історичного дослідження для виконавця

1. За обраним файлом зібрати: owner issue/ратифікацію, чинний machine контракт, архівний source, Git blob SHA, останній механізм.
2. Визначити чи коміт ввів **дослід**, **семантичний закон**, **затверджену карту**, **runtime mechanism** або **тільки fixture/CI**. Не змішувати класи.
3. Локально для вказаного файла: git log --follow -- path; git log -S 'ключовий закон' -- path; git show SHA:path; git blame -L початок,кінець -- path. Git blame визначає появу рядка, НЕ автоматично дату ратифікації.
4. Записати позитивний та негативний свідки SENS; для T5/F3C окремо точні bytes і pinned SHA; для багу — test_id, шар, expected/actual, first bad SHA якщо доведений (інакше UNRESOLVED).
5. Допустиму механічну зміну зробити точково у власному claimed файлі. Якщо бракує нормативного закону, не вигадувати його; створити вузьку конкретну можливість-розв'язати-цікаву-задачу для відповідальної ланки, незалежний рій не зупиняти.
6. Завершити commit SHA + файл/blob SHA + команду відтворення + чесний статус (SOURCE-READY, RUNTIME-UNVERIFIED, VERIFIED-on-exact-SHA). Результат передати у #5029 і discovery board #1599, не покладаючись на статусну фразу агента.
