# Випуск підготовленого snapshot SENS

Цей документ описує **умови** випуску, а не надає дозволу на публікацію кандидата. Наступний кандидат — `s0.42.2` / Cargo `0.42.2` / Contract 12.0; попередній `s0.42.1` уже опублікований. Поточний стан див. у [RELEASE.md](../../RELEASE.md) та [RELEASE-EVIDENCE-s0.42.2.md](../../RELEASE-EVIDENCE-s0.42.2.md).

1. Переконатися, що сім канонічних crates, їхні записи в `Cargo.lock`, Guix та активні asset URL в `packaging/install.sh` узгоджені на `0.42.2`; виконай `bash scripts/check-release-version-alignment.sh`. `scripts/release.lisp` — виведений з ужитку файл-позначка, не драйвер релізу. Не редагувати історичні snapshots/архіви для косметичного усунення старих номерів.
2. Зафіксувати повний SHA поточного `main`; Rust toolchain задається `rust-toolchain.toml` (`1.99.0`). Перевірити provenance і всі зміни на цьому SHA.
3. На **цьому самому SHA** вимагати завершені успішні механічні release-перевірки, нативні SENS-закони з `release-sens-laws.yml`, Release Preflight і платформні збірки. `cargo test --workspace` не є релізним гейтом: він запускає Rust-тести з різних crate, серед яких є перевірки семантики SENS, а Rust не має права визначати мовну істину. Clippy тут лише статично перевіряє механізм; позитивні й негативні мовні вироки дає SENS через фізичний T5M-маршрут. Відсутній прогін або успіх сусіднього SHA не є PASS.
4. Лише після перегляду доказів власник має явно встановити змінні репозиторію `SENS_RELEASE_GO_SHA=<точний 40-hex SHA>` та `SENS_RELEASE_GO_TAG=s0.42.2`. Ці змінні — явний дозвіл власника; автоматично їх не створювати й не підставляти.
5. Після перевірки доказів власник окремо запускає затверджений tag/release workflow для точного SHA. Автоматичний скрипт `scripts/release.lisp` не використовується: файл навмисно виведений з ужитку.
6. Після тегування `release.yml` збирає файли для платформ: CLI для Linux, Windows і macOS (x64/arm64), Windows MSI, обидва веб-REPL та installer. Фінальний крок перевіряє комплект і тотожність байтів повторно завантаженого файлу через `cmp`; публікація можлива лише для точного SHA з `main` та після явного дозволу власника. Квитанції SHA-256 не створюються.

**Будь-яка помилка, невідомий результат або невідповідність SHA означає, що випуск не готовий.** Не послаблювати перевірки й не публікувати частковий комплект. Якщо тег уже створений, але робочий процес випуску не завершився, не пересувати й не переписувати наявний тег; залишити невдалу чернетку для діагностики, виправити `main`, узгодити наступного кандидата та повторити всі перевірки з нового SHA. Опублікований випуск сам по собі не доводить, що файли пройшли перевірку.

Потрібні `git`, авторизований GitHub CLI `gh`, GNU `timeout`, Rust toolchain із `rust-toolchain.toml` та робочий `my-lisp`. Відтворюваність байт-у-байт не обіцяється без pinned runner-image і зовнішніх tool/distribution digests; ці відсутні докази мають залишатися видимими в `RELEASE-EVIDENCE.md`.
