# Добір мови за бенчмарками: Intel Core i5‑6400, Skylake

Мету не визначає назва мови. Для кожного завдання порівнюємо **однакову роботу,
правильність відповіді, час, вартість компіляції й підтримуваність**.
Перший експеримент — скалярний добуток двох масивів по 65536 чисел,
2048 повторів із зміною одного елемента перед кожним повтором.

## Реалізації

| Варіант | Техніка |
|---|---|
| Fortran | Вбудований `dot_product`, `real64` |
| C | Оптимізований послідовний цикл |
| Rust | `f64`, ітератори `zip`, `sum` |
| Zig 0.16 | Власна функція `sens_dot_zig`, цикл над `f64`, C ABI |
| ASM SSE2 | Прямі `mulsd`/`addsd` на x86‑64 |
| ASM AVX2/FMA | Чотири векторні накопичувачі `vfmadd231pd` |

Для C, Zig й обох варіантів асемблера використовується **один драйвер `dot.c`**.
Zig компілює саме `dot.zig` в об'єктний код (`zig build-obj -O ReleaseFast -mcpu skylake`),
який лінкується зі спільним C-драйвером; `zig cc` не видається за реалізацію Zig.
Один машинний файл `crates/sens/src/machine_math_skylake.S` використовується в ядрі SENS
та в бенчмарку — без подвоєння ASM. Виклики Rust `sens::machine_math::dot_f64`
і `squared_norm_f64` перевіряють AVX2/FMA і мають скалярний резервний шлях.
Це лише механізми наближених `f64`, не нові визначення точних D24+.
Усі компілятори отримують одну ціль `-march=skylake` або
`-C target-cpu=skylake` або `zig -mcpu skylake`; без `-ffast-math`. AVX‑512 не використовується.

## Справжній вимір на власному комп'ютері

На UbuntuStudio встановити `gcc`, `gfortran`, `rustc`, якщо їх іще немає.
**Zig 0.16.0** встановити окремо згідно з `.zig-version`;
скрипт перевіряє точний номер версії, інші версії не підміняє.

```bash
sudo apt install gcc gfortran rustc
cd /шлях/до/sens
bash benchmarks/language-fit/run.sh | tee language-fit-i5-6400.md
```

Перед запуском скрипт перевіряє `x86_64`, `avx2`, `fma`. За їх
відсутності він завершує роботу **без запуску несумісного машинного коду**.
Результат містить назву CPU, версії компіляторів і Git SHA.

Правильність порівнюємо з незалежним аналітичним розрахунком.
AVX2/FMA може змінювати порядок додавання чисел із рухомою комою,
тому застосовується явно вказаний відносний допуск `1e-10`.
Кожен варіант проходить прогрів і **п'ять чергованих вимірювань кожної з шести реалізацій**;
звітуємо медіану часу повного процесу, час компіляції, розмір
виконуваного файла та SHA-256 відповідного джерела.

## Автоматичний CI та ручне повторення

Після **кожного push у `main`** уже наявний `.github/workflows/ci.yml`
автоматично запускає порівняння шести реалізацій. Це окреме вимірювання в
одному чинному workflow — без нового workflow, без 19 важких runtime-частин
і без самостійних додаткових повторних запусків. Дослід використовує
той самий `run.sh`. Для PR він не запускається автоматично.

Для повторення вручну: **Actions → Run workflow →
`compare_math_languages: true`**. Ручний режим запускає лише мовний
дослід, без 19 важких частин. Бенчмарк інформативний: відмова вимірювання
публікується як попередження, але не підміняє й не блокує семантичні
перевірки SENS. Результати продуктивності не оголошують автоматичного
переможця.
Після успішної перевірки всіх відповідей GitHub Actions додає
коротку анотацію `notice`: **CPU та шість фактичних медіан, у мс**
(Fortran, C, Rust, Zig, ASM SSE2, ASM AVX2/FMA). Повна таблиця з SHA,
часом компіляції та розміром бінарників залишається в Step Summary.
Анотація не з'являється до перевірки правильності й не встановлює
«переможця» автоматично.

У ручному CI Zig 0.16.0 встановлює вже наявна дія
`.github/actions/install-zig` із перевіркою SHA-256 архіву.

**GitHub-hosted машина — не Intel Core i5‑6400.** Її результати лише
додаткове спостереження; остаточні висновки про власне залізо — за
локальними вимірами. Не робимо автоматичного «переможця» за одним
запуском і не переносимо нормативну семантику SENS до асемблера.

Далі варто порівняти змішані розміри L1/L2/L3/RAM, точну математику,
пакування бітів та потокове введення-виведення, перевіряючи
продуктивність і енергоспоживання окремо.

## Точні знакові D24: перше машинне ядро

`sens::domain_numeric::compute` тепер застосовує `ADD/SUB/IMUL` на x86-64
лише тоді, коли **обидва** операнди вже явно допущені як цілі D24.
Результат повертається точним 24- або 48-бітним двійково-доповняльним
словом згідно з чинним законом зростання; переповнення не замовчується.
Для D48+, NEG/RATIO, ділення та змішаних доменів залишено стару реалізацію.
Немає жодного перетворення в `f64` чи вигаданого нового машинного opcode.
Нативні тести додаються до того самого легкого ручного/автоматичного
бенчмарка; час машинної арифметики оцінюємо окремо від семантичних законів.

## Повне цілочисельне множення D96×D96 → D192

Асемблер x86-64 обчислює **192 біти** без усічення чотирма
частковими добутками `MUL`. Знакову двійково-доповняльну форму
та вибір D96/D192 застосовує чинний доменний закон SENS, без фіктивного
перенесення в `f64`. Для D192×D192 залишається попереднє точне
багатослівне виконання. Додано окремі негативні й крайові тести.
