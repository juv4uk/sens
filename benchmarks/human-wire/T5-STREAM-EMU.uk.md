# Емулятор потоку програм SENS через телеграфний канал T5

**Дата:** 2026-10-08. **Рівень:** MECHANISM / AIR / RESEARCH. **Задачі:** #4447, #2642, #2646, #4173. **Залежність:** обраний файловий T5 у PR #4446. **Призначення:** перевіряти послідовну передачу кількох незалежних програм одним каналом, де довга тиша завершує одну програму, а наступний імпульс починає іншу.

## Що реалізовано

Емулятор `t5_stream.py` (лише Python standard library) перетворює двійкові слова D1–D9 у часові події, потім відновлює потік програм через незалежний інкрементальний приймач. Жодні текстові назви, `2`, паузи, часові пороги або кінцеві кадри не стають новими резидентами SENS. **Він НЕ виконує програму, не є семантичним оракулом і не замінює програмний валідатор D2 у Rust.**

| Подія | Тривалість | Значення в каналі |
|---|---:|---|
| `0` | активний імпульс `1τ` | один змістовий біт `0` |
| `1` | активний імпульс `3τ` | один змістовий біт `1` |
| коротка тиша `1τ` | між двома імпульсами одного слова | не трит `2` |
| тиша `7τ` | між двійковими словами | логічна транспортна межа `2` |
| безперервна тиша `21τ` | після останнього імпульсу програми | фізичний кінець кадру, приймач переходить до наступної програми |

**Це НЕ класичний текст Морзе:** використана лише ідея короткого/довгого імпульсу та розрізнюваних пауз. Не можна називати такий канал автоматично сумісним із міжнародним алфавітом Морзе.

### Відтворювані команди

```shell
# Три послідовні програми за одну передачу; результат JSON з таймінгами
python3 benchmarks/human-wire/t5_stream.py demo

# Записати симульовані mark/gap події у JSON з варіацією тривалостей ±20%
python3 benchmarks/human-wire/t5_stream.py send \
  --program '10 001 01' \
  --program '10 000 01' \
  --program '000' \
  --jitter 0.20 --seed 73 --unit-ms 60 \
  --events /tmp/t5-stream.json

# Приймач не знає початкових програм: відновлює їх ТІЛЬКИ з event timeline
python3 benchmarks/human-wire/t5_stream.py receive --events /tmp/t5-stream.json

# Всі тести
python3 -m unittest discover -s benchmarks/human-wire -p 'test_t5_stream.py' -v
```

`send` збирає список `events: [{kind:mark|gap,units,start_units}, ...]`, але **не кладе очікувані програми** у файл із подіями. `receive` не може шахраювати, підглядаючи у вихідний plaintext; збирає слова за власною машиною станів. Завершення кожної програми визначає лише один останній gap подовженої тривалості.

### Програми передавання

```text
    програма А                  програма Б             програма В
    10 | 001 | 01       [21τ]   10 | 000 | 01   [21τ]  000    [21τ]
    0/1 імпульси з 1τ           0/1 імпульси            0/1 імпульси
    і 7τ паузами               з 1τ і 7τ паузами
```

Дані `10 001 01` і `10 000 01` — ратифіковані точні слова в D1–D9 форматі; для AIR-емулятора вони є **даними**, а не командами на виконання. Довга пауза завершує FRAME, але не підтверджує валідність семантичного дерева. Окреме слово `000` дозволене як top-level атом у чинному читачі Rust.

## Як розрізняється тиша

Для демонстраційного профілю приймач приймає імпульс `0` у вікні 0.5–1.5τ, імпульс `1` у вікні 2.1–3.9τ; проміжний gap 0.5–1.5τ як intra-word; 5–9τ як inter-word; >=14τ як terminal EOF. Інші значення відхиляються як неоднозначні. ±20% jitter для цих номінальних значень не перетинає вікон; реальні ручні характеристики потрібно вимірювати, це **не закон** та не гарантія радіоканалу.

Всі імпульси й паузи, включно з фінальною очікуваною тишею, враховані у `total_timing_units`, `seconds`, `net_semantic_bits_per_second`. Дані за цим режимом — **модельна**, не виміряна швидкість людини.

## FILE EOF не те саме, що AIR EOF

- `.sens` на диску: 5 тритів у байті, транспортна `2` тільки між словами, **файловий EOF замість 22**, 0–4 кінцевих pad-трити `2`.
- AIR-канал: відновлює самі двійкові слова з marks і gaps; тривала тиша сигналізує frame end; **не передає file padding** і не вигадує двох незалежних послідовних тиш.
- Вбудований Python `t5_pack`/`t5_unpack` тільки перевіряє точність фізичного подання файла; GitHub Actions також порівнює Python T5 bytes з Rust `sens-trit encode` на однаковому джерелі.
- Потік уже складається із кількох frame; приймач продовжує роботу після frame-end. Це **не автоматичне виконання отриманих програм**.

## Ризики й запобіжники

1. **Фальшиве завершення:** якщо оператор замислився на 21τ посеред програми, приймач завершить кадр достроково. Емулятор має окремий тест; якщо утворився новий допустимий набір слів, лише CRC/довжина/digest/ACK можуть виявити невідповідність. **Не видавати `frame_received` за `valid_program` або `execution_success`.**
2. **Втрата або вставка імпульсу:** може змінити один біт і залишити цілком допустимий файл. Алгоритму потрібна інша цілісність перед довіреним LOAD (#2646).
3. **Синхронізація й радіотиша:** реальна втрата несучої не доводить, що передавач завершив програму. Це дослід, не схвалений реальний ефірний протокол.
4. **Word identity:** `0 | 00` та `000` мають однакову конкатенацію, але наші 7τ паузи і typed digest дозволяють їх розрізнити.
5. **Number D24+, повна uk/укр поверхня, оракул семантики:** цим емулятором не реалізовані. Відсутність цього підтвердження не можна замовчувати.
