**11.10.2026.** Актуальний SHA доказу: `26ad982c0e64f886262dd4a602cf4bb4246697b7`.
GitHub Actions [38162725571](https://github.com/juv4uk/sens/actions/runs/38162725571):
**обидва jobs SUCCESS**; вихідні сирі результати, точні SHA, усі застереження нижче.
Rust SENS evaluator, Rust фізичний T5/D2 reader, а не вигадана модель виконання.

## 1 байт: одна справжня обчислювана програма

**Джерело:**
[фізичний Git blob](../../../research/framed3/fixtures/car-cons-one-nil.f3m)
(`9fb75b8d4f4c7faa7ba59d138746231ada07c7b0`, рівно 1 байт `0x45`).

Зовнішньо оголошений експериментальний профіль `.f3m` відновлює:

```
10 100 10 111 1 000 01 01
```

Точні домени D2/D3/D1: `CAR(CONS(1,NIL))`. Реальний Rust SENS
інтерпретатор виконує CONS → CAR і повертає
`DomainIdentity(DomainIdentity<D1>(1))`. Незалежний чинний шлях
`PhysicalT5Program::decode(...).execute(...)` повертає той самий
результат та побічні виходи. **1 байт .f3m проти 5 байтів повного T5**
для цієї ж точної програми (5× менше саме на цьому корпусі).

Це НЕ скорочення за назвою в тексті: дослідний декодер алгоритмічно
відновлює кожне D1–D3 слово за класом виклику та позиціями аргументів.
Є **45** скінченних закритих правильних програм цієї grammar family,
і всі 45/45 успішно перевірені Rust evaluator ↔ physical T5,
також перебрано всі 256 можливих кодових байтів і відхилено невиділені
та неправильну фізичну довжину.
Комітований фізичний байт сверджено через `include_bytes!` і `cmp`
із випущеним `.f3m` файлом. [Сирий TSV та два фізичні файли](https://github.com/juv4uk/sens/actions/runs/38162725571/artifacts/11711027228).

**Важливе обмеження:** `.f3m` — експериментальна **мікрограматика
зі заздалегідь відомим декодерові профілем**. У реальному 1 байті
НЕ закодовано вибір профілю, довільний код програми, version-поле,
checksum/CRC чи сам декодер. Це чесний доказ здійсненності **для
скінченного класу осмислених закритих програм**, а не нинішній
production-файл `.sens` або доказ, що будь-який код можна стиснути
в один байт. При зміні одного дійсного байта на інший дійсний
контроль цілісності тут не гарантований.

Резервні коди не слід автоматично переінтерпретовувати через T5:
неявний fallback зробив би формат недвозначно невідновним без
попередньої угоди про профіль.

## Звичайні фізичні файли, а не повторювані W9

[Парні результати — GitHub Actions](https://github.com/juv4uk/sens/actions/runs/38162725571).
[Повний TSV пофайлово](https://github.com/juv4uk/sens/actions/runs/38162725571/artifacts/11711027228)
містить також мікропрограмний експеримент; інший артефакт
`frame3-real-file-*` доступний у тому самому Actions запуску.

Програма `frame3_real_files_bench.rs` бере **всі Git-tracked
`*.sens`**, без ручного вибору найкращих; кожен файл спершу
допускається Rust `PhysicalT5Program::decode` і робить
byte-exact `decode_ternary_words` ↔ `encode_ternary_words`.
Лише після цього перевіряється **оригінальна F3**, з повною фізичною
однобайтовою міткою `F3` і точним `senc::decode_senc` roundtrip.

| Метрика | Виміряно |
|---|---:|
| Git-tracked фізичних файлів `.sens` | 23 |
| Прийняв чинний Rust T5/D2 reader | 23 |
| Повний F3 roundtrip підтримує | 12 |
| F3 unsupported / noncanonical | 11 |
| Сума повних T5 байтів лише на 12 прийнятих | 94 |
| Сума повних F3 байтів з міткою лише на тих самих 12 | 83 |
| Економія на **підмножині 12/23** | 11,702% |

Приклади без прихованого overhead: `quote-legacy.sens` T5 4 → F3 3 байти;
`pair-cons.sens` 10 → 9;
`pair-car-cdr.sens` 11 → 10;
`eq-lisp15.sens` 5 → 5.
Більші багатоформні/складні файли нинішня F3 не допускає:
їх не можна зараховувати як стислий результат.

**Швидкість:** нинішній дослідний Rust F3 надто дорогий на CPU,
особливо для коротких файлів; бенчмарк фіксує окремо повні фізичні
розміри та p50 теплих encode/decode, не runtime execution і не cold start.
Тому не рекламувати прискорення чи глобальну перемогу.

## Яку задачу ставить це для нового універсального Rust-кодека #5439

1. Зробити обмежене grammar-rank подання одним із формально доведених
   режимів **самого нового універсального формату**, не стороннім
   обов'язковим профілем; обов'язково врахувати селектор, EOF, довжини
   точних доменів, незайняті ранги, version/integrity та bytes у ціні.
2. Перевірити, чи однобайтові коди можна розмістити як самодостатні
   короткі префікси **нового** формату, не підмішуючи старий T5
   чи роблячи небезпечне content autodetection. Для міграції старих
   1B T5-файлів потрібна явна відокремлена політика.
3. Збільшити підтримку **23/23 реальних** файлів та довших програм;
   жодного фальшивого `supported` і жодної втрати `00/01/10/11`,
   leading zero або семантики QUOTE.
4. Зменшити повільний rank/unrank на CPU; продовжити парні вимірювання
   на однакових SHA та реальних файлах, знімати p50/p95, cold start,
   пам'ять. Не оголошувати byte optimality без повного DP доказу.
5. Rust↔Python parity з попередньої матриці F3 має 1062 розбіжності
   з 1703; цей однобайтовий proof їх **не розв'язує**.
   Fail-closed негативні тести залишаються обов'язковими.
