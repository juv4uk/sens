# WebAssembly reality lane (#3681)

This lane asks a narrow question first: for the same two current D3 smoke observables,
what do **program artifact size**, **load/decode/compile**, and **already-ready execution**
look like for canonical SENS versus a minimal executable WebAssembly module?

## Scope and fairness boundary

Current SENS side:

```
canonical exact-domain source
 -> production exact-width packer
 -> parse_canonical_binary
 -> lower_program
 -> DomainIdentity
 -> eval_lowered_expressions
```

WebAssembly control side:

```
minimal .wasm module
 -> WebAssembly.Module (decode + validate + compile)
 -> WebAssembly.Instance
 -> exported run()
```

The Wasm controls are handwritten binary modules generated by `wasm_module.py`; they do
not carry Rust/C compiler baggage.

Two fixtures are admitted initially:

- `d3-quote-empty` — Wasm `run()` returns i32 zero;
- `d3-car-empty` — Wasm owns an 8-byte pair in linear memory and `run()` loads its head.

i32 zero is mapped to the fixture's observable structural empty `()` **only for this
mechanism control**. This does not make Wasm i32 zero a SENS semantic identity.

## What is directly ranked

When run in `performance` mode on one controlled machine:

- canonical program artifact bits/bytes — generic runtimes excluded on both sides;
- already-ready execution ns/op.

## What is recorded but not ranked

- SENS canonical ingest vs `WebAssembly.Module` compile: Wasm compile includes validation
  and machine compilation, while SENS ingest is exact-domain parsing only;
- cold totals: the SENS path includes current Core/session preparation and the Wasm path
  assumes the host engine already exists;
- RSS until shared owner #3698 lands.
