# Як логічний трит «2» реалізувати тими самими фізичними 0 та 1

Статус: **дослідне транспортне кодування** #4438, PR #4443; семантика мови **залишається двійковою**. Це НЕ новий D10 резидент.

## Контракт

Префіксне кодування логічних транспортних символів:

| Транспортний символ | Фізичний двійковий код |
|---|---|
| 0 = біт SENS 0 | `0` |
| 1 = біт SENS 1 | `10` |
| 2 = межа двійкових слів | `11` |

Жоден із кодів `0`, `10`, `11` не є префіксом іншого. Декодер читає зліва направо: `0` => дані 0, `10` => дані 1, `11` => кінець слова. Це дає **однозначний транспорт без трійкового апаратного носія**, а вихідні бітові функції SENS не змінює.

**Дослідна** умова EOS: два маркери `11` поспіль **після непорожнього слова**, тобто останні 4 змістові фізичні біти `1111`. Після них до кінця останнього байта дозволено лише нульовий хвіст (< 8 фізичних бітів); додатковий байт заборонено. Ні EOS, ні ці допоміжні коди не є D2 та не стають частиною SENS-граматики.

Контроль `0 | 00` проти `000`: вони мають однаковий голий payload `000`, але різні межі; з кодом `11` дають різні фізичні послідовності й декодуються назад без `.lisp`.

## Вартість порівняно з base-3 byte packing

Нехай `S` — сума ширин двійкових доменних слів, `U` — кількість одиниць серед цих бітів, `N` — число слів.

- Префіксне фізичне двійкове кодування: `S+U+2*(N-1)+4` бітів; файл займає `ceil(encoded_bits/8)` байтів.
- Трійкове кодування 5 тритів/байт: `S+(N-1)+2` тритів; файл займає `ceil(encoded_trits/5)` байтів.

Обидва способи однозначно відновлюють межі; обидва мають фізичну вартість, яку не можна називати бітами мови. Число тритів не дорівнює числу фізичних бітів.

Для прикладу `10 | 001 | 00 | 000 | 01`: `S=12`, `U=3`, `N=5`. Двійковий код має `12+3+8+4=27` кодових бітів та **4 фізичні байти**; трійковий складається з 18 тритів, також **4 фізичні байти**.

Для восьми D9 слів, кожне `000000000`: двійкове кодування має 90 змістових транспортних бітів → **12 байтів**, 5-тритний код має 81 трит → **17 байтів**.

Для восьми D9 слів, кожне `111111111`: двійкове кодування має 162 транспортних біти → **21 байт**, 5-тритний код має 81 трит → **17 байтів**.

Отже немає універсального переможця: двійкове кодування виграє на нулях, трійкове може бути компактнішим для одиниць. При виборі остаточного формату враховувати типові програми, короткі слова, частоту 1 і вартість читача.

## Наявна дослідна реалізація

`crates/sens/src/binary_delimited_transport.rs`: `encode_binary_delimited_words`, `decode_binary_delimited_words`, `encode_binary_delimited_projection`, `decode_binary_delimited_program`, `binary_delimited_accounting`. Регресійні тести: кожне можливе D1…D9 слово, колізія старих меж, D7 sign.space у payload, зайвий байт, відмінність на серіях нулів/одиниць. Реальна семантика і арність перевіряється лише на вході/виході через наявний `parse_canonical_binary` для вже видимих точних D1..D9; oracle parity не доведена.

Ще потрібні: власниковий вибір фізичного codec; ратифікований EOS/tail; Number D24+ value layout; українська `uk/укр` → ратифіковані доменні коди; справжні програми та повні семантичні тести. Додаткові **мовні** функції, якщо з'являться, заносити до #4013, не змішувати їх з носієм.
